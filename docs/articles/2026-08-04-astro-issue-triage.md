## TL;DR

- 「ソフトウェアファクトリー」（AIエージェントをパイプラインとして組み合わせ、自律的にソフトウェアを生み出す仕組み）は議論の的になっているが、Cloudflareが持つのは実際の成果である。
- Astroリポジトリ上で、着信するバグ報告を読み取り、サンドボックスで再現し、根本原因を診断し、報告者が検証できるプレビューリリースを配布する自動トリアージパイプラインを数か月間運用してきた。
- この仕組みの中核エンジンは **Flue** という、この種のエージェント自動化を構築するためのオープンなフレームワークへと発展した。
- オープンなIssue数を200件超から約30件まで減らすことに成功し、数か月以内にゼロを達成する見込み。これはAstroリポジトリ5年以上の歴史で初めてのことになる。
- 「issue bankruptcy（Issueの一括破棄）」宣言や、古いチケットの自動クローズ、報告の無視といった手段は一切使わず、GitHub Actions上で動く隔離されたAIサブエージェントのチームによってIssueトリアージを自動化した。

## 背景・課題

「ソフトウェアファクトリー」というアイデア——AIエージェントをパイプラインとして組み合わせ、工場が原材料を完成品に変えるように、自律的に動作するソフトウェアを生み出すというコンセプト——について、誰もが語っている。それが本当に可能なのか、自動化はどこまで進むのか、デモされている「ループ」に本当に価値があるのかをめぐって、終わりのない議論が続いている。すでに失敗だったと結論づける声もある。

その裏側で、より静かで、より切実な会話も進行している。オープンソースのメンテナーたちが燃え尽きているという問題である。AIブームによって、Issue・プルリクエスト・セキュリティレポートを生成するコストはほぼゼロになった一方、メンテナーがそのすべてに目を通すコストは膨大になった。プロジェクトを健全に保つための従来のやり方は、この量の前で崩れ始めている。

誰もがこの2つの話題について持論を持っているが、Cloudflareが提供できるのはもっと希少なもの——実際の成果である。過去数か月間、Astroリポジトリ上で自動トリアージパイプラインを運用してきた。バグ報告を読み取り、サンドボックス内で再現し、根本原因を診断し、報告者が検証できるプレビューリリースを配布する、という一連の流れである。この仕組みを支えるエンジンは **Flue**（この種のエージェント自動化を構築するためのオープンなフレームワーク）へと発展し、誰でも自分のプロジェクトを構築するために使えるのと同じツールになっている。

一夜にして成功したわけではない。しかし、多くの試行錯誤を経て、オープンなIssue数を200件超から約30件まで減らすことができ、今後1か月ほどでゼロに到達する見込みだという。これは、5年以上の歴史を持つこのリポジトリで、オープンIssueがゼロになる初めての出来事になる。

この成果は、「issue bankruptcy（Issueの一括破棄）」を宣言したり、反応の止まったチケットを自動クローズしたり、報告を無視したりすることで達成されたのではない。GitHub Actions上で動く、隔離されたAIサブエージェントのチームによってIssueトリアージを自動化することで実現された。

## 発表内容 / アーキテクチャ

### エージェントスキルから始める

年の初め、Astroチームは開発の一領域——Issueトリアージ——の自動化に絞って取り組み始めた。オープンソースプロジェクトにおいて、手作業でのIssueトリアージは、時間がかかる割に報われることの少ない作業の1つになりがちである。1件のIssueを再現するだけで数時間かかることもあり、修正はさらにその先にある。それにもかかわらず見過ごされがちなこの領域が、自動化の出発点として選ばれた。

まず、**エージェントスキル**を開発するところから始めた。これにより、メンテナー自身のマシン上でコーディングハーネスを実行しながら、ローカルで自動化を開発・テストできた。そして、同じハーネスをGitHub Action上でリポジトリに対して実行することで、まったく同じトリアージワークフロースキルを完全に再利用できるようになった。

このトリアージスキルは、手作業でのIssue解決時に踏んでいるのと同じステップを模している。

1. **Reproduce（再現）**: 提供された再現用リポジトリをクローンし、報告されたIssueを検証する。
2. **Diagnose（診断）**: コードベースを計装し、ログを仕込んで根本原因を特定する。
3. **Verify（検証）**: 関連するテストスイート・コードコメント・ドキュメントを確認し、それが本当にバグなのか、それとも意図された挙動なのかを判断する。
4. **Fix（修正）**: 再現手順を失敗する単体テストに変換し、アーキテクチャガイドを参照して適切な解決策を特定し、修正をデプロイする。

LLMにありがちな「バグが実際には存在しなくても解決策を無理やり作り出そうとするバイアス」を防ぐため、各フェーズは**隔離されたサブエージェント**によって実行される。これらのサブエージェントは、それぞれの発見内容を `report.md` ファイルにまとめることで、情報を順番に後続へ引き継いでいく。

### スキルを自動化へ発展させる

トリアージスキルの社内テストを経て、焦点は完全に自動化されたパイプラインの構築へと移った。特に、このロジックをGitHubワークフローに直接組み込み、誰でもエージェントの推論と実行手順を順を追って監査できるだけの透明性を確保することを重視した。

構築を進める中で、このパイプライン全体が実質的に**Issueラベルによって駆動されるステートマシン**であることに気づいた。新しいIssueは `triage needed` ラベルから始まり、ユーザーが修正を確認すると `fix verified` に移る。ラベルの遷移以外に、パイプライン自体は状態を持たない。単に、Issueの既存コメントを読み返すことで、そのIssueが今どの段階にあり、次に何をすべきかを判断している。

そこから先はパイプラインが自律的に進む。エージェントが修正にたどり着くと、パイプラインは `pkg.pr.new` を使ってプレビューリリースを立ち上げ、発見内容の要約・完全なログ・インストール手順をまとめてIssueに投稿する。元の報告者はそのパッチを自分のプロジェクトに対して試すことができ、動作を確認できればその自動化がIssueにひも付いたプルリクエストを自動的に開く。

### トリアージからフレームワークへ

こうして構築を進めるうちに、この仕組みにはGitHub固有の部分がほとんど何もないことに気づいた。イベントに反応し、隔離されたサブエージェントの列を実行し、その推論と実際に取れるアクションを分離する——これはすべて単なる**ワークフロー**である。GitHub Issueからだけでなく、Slackのメッセージ・cronジョブ・Webhookからでも同じように動作しうる。この気づきを、どこにデプロイされていても、どのモデルを動かしていても同じように機能するランタイムへと一般化したものが **Flue**——耐久性のあるエージェントとワークフローを構築するための、オープンでプラットフォームに依存しないフレームワークである。

### エージェント自動化がもたらした効果

この自動化システムを最初に立ち上げたとき、その有効性や、開発者コミュニティへの悪影響について懸念を共有していた。自動化されたボットの応答に頼ることで、事務的で人間味のない印象を与え、メンテナーとユーザーの間にさらなる断絶を生んでしまうのではないか、という正当な不安があった。

しかし、そうはならなかった。むしろ、以前よりもユーザーと対話する機会は増えており、その場もより有意義なものになっている。

- Discord上でコミュニティメンバーと直接エンゲージメントする
- RFCの議論に積極的に参加し、新機能のリクエストに対応する
- コントリビューターと緊密に協力し、彼らのアイデアをフレームワークに統合する

自動化されたパッチの品質については、着信するIssueの大多数をAIエージェントが解決できるべきだ、というのが基本方針である。エージェントが正しい解決策を見つけられなかった場合、それをコードベース側のアーキテクチャやドキュメントに潜む問題の兆候だと捉える。具体的には次の3つの領域のいずれかを指すと考えている。

- **不透明な抽象化（Opaque Abstractions）**: エージェントがコンポーネント間の境界を解釈できないなら、人間の開発者も同じようにコード構造に苦労している可能性が高い。
- **ドキュメント不足（Missing Documentation）**: 重要なコード部分に、その実装の意図を説明する明示的なコメントが欠けている。
- **テスト不足（Insufficient Testing）**: リポジトリに包括的なテストカバレッジ、特に単体テストが不足している。

分かりやすい例として、一連の関連するHMR（Hot Module Replacement）のバグが挙げられている。トリアージボットは、Issueを解決するために特定の `if` 条件を繰り返し修正しようとした。この変更で対象のバグは修正できたものの、その条件に対するテストカバレッジが不足していたため、別の箇所で回帰（リグレッション）を引き起こしてしまった。その条件が持つ正確なロジックを説明する記述的なコメントを追加したところ、ボットはそれに適応し、その領域で誤った修正を試みなくなった。

こうした失敗を1つずつ追跡し、欠けていたコメント・テスト・境界の明確化を加えるたびに、ボットはコードベースのその部分についてはっきりと賢くなり、次にそこを担当する人間の開発者にとっても同じ効果が得られる。

### ワークフローをGitHub Actionへ

当初、トリアージのロジックはAstroのモノレポ内に直接組み込まれていた。この結合が、反復開発を難しくしていた。Flueをアップグレードしたり、ワークフローを修正したりすることは、安全網なしで稼働中のインフラに手術を施すような作業に感じられた。これを解決するため、ロジックを独立したテスト可能なリポジトリ **triagebot-action** へと切り出した。この分離によって、本体のコードベースに触れる前に自動テストを導入し、安定性を確保できるようになった。

現在、このActionはAstroのIssue管理を支えており、そこからさらに他のチームへも広がっている。直接利用するチームもあれば、フォークして自分たちのプロジェクト向けに独自の「ファクトリー」を構築するチームもある。後者こそがまさに狙いである。triagebot-actionはまだ若く、現在も活発に進化し続けているため、完成品としてではなく、読み・学び・改造できる「動くリファレンス」として共有している。

## コード例

記事では、`triagebot-action` をGitHub Actionsワークフローから呼び出す設定例が示されている。

### GitHub Actionとしてのtriagebot-actionの呼び出し

```yaml
- uses: withastro/triagebot-action@v1
  with:
    read-token: ${{ secrets.GITHUB_TOKEN }}
    write-token: ${{ secrets.BOT_GITHUB_TOKEN }}
    cloudflare-api-key: ${{ secrets.CLOUDFLARE_API_KEY }}
    cloudflare-account-id: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
    triage-model: cloudflare-workers-ai/@cf/moonshotai/kimi-k2.7-code
    verification-model: cloudflare-workers-ai/@cf/moonshotai/kimi-k2.6
    triage-skill: .agents/skills/triage
```

**解説**: `withastro/triagebot-action@v1` を呼び出すだけで、Issueトリアージパイプライン全体をワークフローに組み込める。`read-token`／`write-token` はGitHubへの読み書き権限を分離するためのトークンで、書き込み（コメント投稿やPR作成など）専用のボットアカウントのトークンを別に用意していることが読み取れる。`cloudflare-api-key`／`cloudflare-account-id` はCloudflare上でエージェントを実行するための認証情報である。特に注目すべきは `triage-model` と `verification-model` の2つで、トリアージ（再現・診断・修正）用にはコード生成に強いモデル（`kimi-k2.7-code`）、確認用にはもう一方のモデル（`kimi-k2.6`）と、フェーズごとに異なるモデルを使い分けている。`triage-skill` は、リポジトリ内に配置されたエージェントスキルの定義ファイルへのパスであり、「エージェントスキルから始める」で述べた、ローカルとCI双方で再利用される同一のトリアージスキルを指している。

## ユースケース

### OSSリポジトリのバグ報告トリアージ自動化

Astroリポジトリ上での本命のユースケース。着信したバグ報告を、隔離されたサブエージェント（再現・診断・検証・修正）が順番に処理し、`pkg.pr.new` によるプレビューリリースを報告者に提示して検証を依頼する。報告者が確認できれば、Issueにひも付いたプルリクエストが自動的に作成される。

### コードベースの品質改善サイクル

エージェントがIssueを解決できなかった場合、それを「不透明な抽象化」「ドキュメント不足」「テスト不足」のいずれかの兆候として扱い、コメント・テスト・境界の明確化を追加する。これにより、ボットだけでなく人間の開発者にとってもコードベースが理解しやすくなっていくという、継続的な品質改善のフィードバックループが生まれる。

### 他プロジェクトへの横展開（triagebot-action）

Astro向けに構築されたtriagebot-actionは、独立したリポジトリとして切り出されたことで、他のチームが直接利用したり、フォークして自分たちのプロジェクト向けの「ファクトリー」を構築したりする土台として使われている。

## 所感・ポイント

- 「ソフトウェアファクトリー」という言葉が大きな議論を呼ぶ中で、Astroチームは派手な主張をするのではなく、「Issue数200件超→約30件、まもなくゼロ」という定量的な実績を淡々と示している点が印象的である。抽象的な可能性論ではなく、実運用の数字で語るアプローチは説得力がある。
- 「トリアージスキルをローカルのコーディングハーネスとGitHub Actionsの両方で完全に再利用する」という設計は、自動化の第一歩として「まず人間が使えるツールを作り、それをそのまま自動化に転用する」という堅実な進め方の好例である。
- エージェントが失敗した原因を「エージェントの能力不足」ではなく「コードベース側の不透明な抽象化・ドキュメント不足・テスト不足」に帰着させ、そこを直すことでボットと人間の両方にとってコードベースが改善されていく、というフィードバックループの発想は、AIエージェント導入を「コード品質向上の駆動力」として位置づける興味深い視点である。

> **Workers サンプル**: 対象外（中核はGitHub Actions上で動くtriagebot-action／Flueフレームワークによる自動化であり、Cloudflare Workersとしてデプロイする対象ではないため）
