# ID情報に基づく分析で、不正なAIの利用を検出

## TL;DR

- AI利用の請求書だけを見ても異常は判断しづらいが、「通常の利用パターン」を把握できれば、エージェントの暴走や特定社員の利用急増に気付ける。
- Cloudflare Accessと連携する**Identity-aware AI Gateway**がオープンベータで、すべてのAI Gatewayリクエストに確認済みのユーザーIDを紐付けられるようになった。
- **User Insights**がAI Gateway利用者全員に追加費用なしで一般提供され、ユーザー・エージェントごとの「普段の利用パターン」を学習し、そこから外れた利用を検知する。
- 異常判定は固定のしきい値ではなく、そのアカウント自身の過去30日間のセッションコストのp95（95パーセンタイル）の2倍、かつ組織全体のp99（99パーセンタイル）を超えるかどうかという相対的な基準で行う。
- 早期導入企業のFlexportでは、共有APIキーでは不可能だった「誰が使っているか」の特定と、既存のID管理ポリシーの適用が可能になったという。
- 今後、プロンプト内容の自動分類（コーディング／文章作成など用途の分類）や、コストとクオリティのバランスを取るタスクベースのスマートルーティングの開発も予定されている。

## 背景・課題

AIの月次請求額を眺めるだけでは、その支出が妥当かどうかを判断するのは難しい。しかし「通常の利用状況」という基準があれば、そこからの逸脱を検知でき、調査を始めるきっかけになる。これまでは、この「通常からの逸脱」を確認する手段自体が乏しかった。

AIによる「誰が」「何をしているか」の把握は、多くの組織が直面する主要な課題である。記事が引用するスタンフォード大学の調査では、59%の組織が「責任あるAIガバナンスの最大の障害は知識不足である」と回答している。この問題は金銭的な側面だけでなくセキュリティにも直結する。課題を解決するには、（1）すべてのリクエストに確認済みのIDを紐付けること、（2）そのIDの普段の利用状況を把握すること、という2つの要素が必要だと記事は位置づけている。

## 発表内容 / アーキテクチャ

### AI Gatewayという中央管理基盤

AI Gatewayは、組織内で使われるすべてのAI利用を一元管理する基盤である。各アプリ・チームがOpenAI、Anthropic、Google、Workers AIのモデルを直接呼び出すのではなく、まずAI Gatewayを経由させることで、すべてのAI利用を横断的に観察・保護・管理できる。自社開発アプリだけでなく、Claude Code、Codex、GitHub Copilotなど開発者が日常的に使うコーディングツールもAI Gateway経由にでき、これらも他のAI利用と同じように可視化・アクセス制御の対象にできる。

### Identity-aware AI Gateway

AI GatewayとCloudflare Accessを連携させることで、ゲートウェイの前段にバニティドメインを置き、他のアプリケーション同様にAccessで保護できるようになった。これにより以下が可能になる。

- OktaやEntraなど、SAML対応の任意のIDプロバイダーでの認証（Cloudflare APIキーを個別に生成・共有する必要がなくなる）
- 誰がゲートウェイにアクセスできるかを細かく管理するポリシー設定
- アカウントIDやゲートウェイIDをURLに含めず、`ai.example.com`のようなシンプルなホスト名でリクエストを送信

Accessで認証されたすべてのリクエストにはユーザーのID情報が付与され、AI Gatewayは確認済みのAccessユーザーIDを`cf.user_id`というリクエストメタデータに追加する。これにより、実際にリクエストを実行したユーザー単位でログ・分析情報・AI利用料金を確認・集計できる。

さらに、利用料金の上限設定と組み合わせることで、ユーザーごとの予算管理も可能になる。各ユーザーに個別の予算枠を割り当て、上限に達したらリクエストをブロックしたり、より安価なモデルへ自動的に切り替えたりできる。これにより、予期しない高額請求の防止と、「共有APIキーでは誰がどれだけ使ったか分からない」という問題の解消につながる。

早期導入企業のFlexportでスタッフセキュリティエンジニアを務めるMax Baumgarten氏は次のように述べている。「共有APIキーでは、誰がAIサービスを利用しているのかを把握することがほぼ不可能であり、従業員向けに設定している既存のアクセスルールを適用することも困難です。Cloudflare AccessをAI Gatewayの前段に配置することで、各リクエストに認証済みのIDを付与でき、既存のID管理ポリシーをゲートウェイで利用できるようになります。チームはクライアントごとに個別の認証システムを構築することなく、AIツールを導入できます。」

今後は、IDプロバイダー上のグループ情報を利用して、利用料金の上限設定やアクセス可能なモデルの制御ができるようになる予定である（例: 機械学習チームには最新モデルへのアクセスを許可する一方、サポートチームには利用料金の上限を設定する、特定プロジェクトのメンバーだけに予算枠を設定する、など）。

### User Insights: 行動パターンからの異常検知

AI Gatewayに新設された「User Insights」タブは、ゲートウェイを通過する通信を分析し、各アカウントの利用状況・行動パターンを表示する。それぞれのアカウントの通常の利用パターンを学習し、そこから外れた利用を特定した上で、その変化が「不正なAIエージェントによる異常な動作」なのか「単に作業量が増えたエンジニアによる利用増加」なのかを判断するための材料を提供する。すでにAI Gatewayを通過している通信を使うため、新たな設定や追加の導入作業は不要である。コスト管理の観点でも、キャッシュヒット率の低さや必要以上に大きなコンテキストウィンドウの使用といった、コスト増加要因の把握に役立つ。

**すべてのアカウント（ユーザーとAIエージェント）の行動を基準化する**。人間とAIエージェントでは利用パターンの性質が異なる。例えば3時間ごとに問い合わせ内容を要約するエージェントの行動パターンは安定している一方、人間のユーザーはプロンプト内容・利用時間帯・難しい課題への長時間の取り組みなどによって利用パターンが不規則になる。どちらも正常な利用だが、同じような変化が起きても、エージェントでは異常の兆候となる一方、人間では単なる利用のばらつきに過ぎない場合がある。

User Insightsは個々のリクエストではなくセッション単位で評価する。単純な固定しきい値ではこの違いを正しく判断できない。普段から利用量が多いユーザーが500ドル多く使ってもそれは通常の範囲かもしれないが、普段5ドル程度しか使わないエージェントが50ドル使えば利用量が10倍に増えたことになり、重大な異常の可能性がある。しかし固定しきい値だけではこうした変化を見逃してしまう。そこでUser Insightsは、各セッションをそのアカウント自身の過去の利用履歴と比較する。

具体的には、過去30日間のセッションコストのp95（95パーセンタイル）を「そのアカウントの普段の利用量」の基準値とし、セッションコストがその2倍を超えた場合に異常な利用の可能性が高いと判断する。

![セッションコストの異常検知](https://blog.cloudflare.com/_emdash/api/media/file/01KZ7B4VMH9D9FYZTWDMRSWZJS.png)
*図1: セッションコストの異常検知。Cloudflare社内の実データを基にした散布図で、X軸がセッションコスト（対数スケール）、Y軸がそのユーザー自身のp95基準値に対する倍率（対数スケール）を表す。2本の破線が「2× User p95」と「アカウント全体のp99」を示し、両方を超える右上（★印）の領域のみがアラート対象になる（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

この図が示す4つの領域は次の通りである。

- **右上（★印）**: ユーザーごとの基準値（2× User p95）と、アカウント全体の上限値（p99）の両方を超える。通常より大幅に利用量が増えている異常な支出と判断され、アラート対象になる。
- **左上**: ユーザー自身の基準値は超えるが、アカウント全体のp99には達しない。少額の利用増加による不要なアラートを防ぐため、異常として扱わない。
- **右下**: セッションコスト自体は高額だが、そのユーザーにとっては普段からその程度の利用があるため通常の利用と判断される。
- **左下**: どちらの基準値も超えておらず、通常の利用と判断される。

なぜ組織全体のp99を「絶対的なコスト上限」として併用するのか。それは「特定ユーザーが普段より多く使った」というだけでは異常と判定させず、組織全体で見ても上位1%に入るほど高額なセッションである場合に初めて異常の可能性ありと判断するためである。

![アカウント全体のセッションコスト分布](https://blog.cloudflare.com/_emdash/api/media/file/01KZ7B4V6XV5D14V3FW55YHKTZ.png)
*図2: アカウント全体で見たセッションコストの分布のヒストグラム。大半のセッションコストは10ドル未満でp95は20ドル、アカウント全体のp99（200ドル）を超えるセッションは全体のわずか1%（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

基準値は固定ではなく、アカウントの利用傾向の変化に合わせて自動的に更新される。

![単一ユーザーのセッション履歴](https://blog.cloudflare.com/_emdash/api/media/file/01KZ7B4VJ083H8C3Q82M6D6Q6W.png)
*図3: 単一ユーザーのセッション履歴。過去30日間のp95（緑線）とその2倍のしきい値（オレンジ線）が、利用傾向の変化に応じて時系列で自動的に更新される様子を示す（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

さらにコストには最低金額も設定されている。アラートが発生するには「統計的に見て通常とは異なる利用」であるだけでなく「管理者が調査する価値がある程度の金額」であることも条件となる。これにより、普段ほとんど利用しないユーザーが数セントしか使っていないのに、その金額が500倍に増えたようなケースでも、実際の金額がごくわずかであればアラートは発生しない。

**不正な利用を検出するための最適な視点**。ここまでの分析を経て、管理者には通常の利用を除外し、それぞれのアカウントが自身の通常パターンから外れた利用だけを表示する画面が提供される。不審な利用の一覧フィードとして機能する。

![異常な利用状況の概要](https://blog.cloudflare.com/_emdash/api/media/file/01KZBWJPJZPCZJYCR5D89H0DZ3.png)
*図: 異常な利用状況（組織全体の概要）画面（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

![異常な行動のセッション別分類](https://blog.cloudflare.com/_emdash/api/media/file/01KZ7B4VJEZHBRF1215EYNX2GW.png)
*図: 異常な行動をセッション別に分類した画面（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

こうした不審な利用は、「新しいツールを使い始めた」「禁止操作を行った」といった分かりやすい兆候ではなく、信頼されたアカウントによる許可済みの実行内容であるため捕捉が難しい。例えば、サービスアカウントが突然これまでより高額なセッションを実行し始めたり、あるユーザーの利用量が通常水準を大きく超えた状態が数日間続いたりするケースが該当する。これらはいずれもアクセス制御ポリシーには違反していないが、そのアカウント本来の利用パターンから大きく外れている。こうした兆候は、資格情報が不正利用された、あるいはエージェントが想定外の動作を始めた最初のサインであることが少なくない。

![ユーザー単位の詳細データ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ93AY5C3BJQW575MS95PZXC.png)
*図: ユーザー単位の詳細データ画面（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/identity-aware-ai-gateway/）*

User Insightsは利用者の意図を判断したり自動的にブロックしたりするものではなく、通常パターンから外れた行動を始めた少数のアカウントを管理者に提示し、「何が起きているか」を確認できるようにするものである。本格的なセキュリティ調査に発展する場合もあれば、単にユーザーへの指導（例: 開発者がコード全体を必要以上にプロンプトへ貼り付けてしまうケース）で済む場合もある。

## コード例

本記事にはコード例の掲載はない。User InsightsおよびIdentity-aware AI Gatewayはいずれもダッシュボード上の分析機能・認証連携機能であり、記事も統計的な異常検知の仕組み（パーセンタイルによるしきい値設計）の解説が中心になっている。

## ユースケース

### 共有APIキー運用からの脱却（Flexportの事例）

Flexportでは、共有APIキーでは「誰がAIサービスを利用しているか」を把握できず、既存のアクセスルールも適用できないという課題を抱えていた。Cloudflare AccessをAI Gatewayの前段に置くことで、各リクエストに認証済みIDを付与し、既存のID管理ポリシーをそのままゲートウェイに適用できるようになった。

### ユーザー・チーム単位の予算管理

`cf.user_id`によってユーザー単位でのAI利用料金の集計・上限設定が可能になり、想定外の高額請求を防ぎつつ、上限到達時により安価なモデルへ自動切り替えるといった運用ができる。

### インサイダーリスク・資格情報不正利用の早期検知

普段5ドル程度しか使わないサービスアカウントが突然50ドルのセッションを実行した場合など、固定しきい値では見逃されがちな異常を、アカウント自身の履歴と組織全体の分布の両方から検知できる。エージェントの暴走や、盗まれた資格情報によるAI利用の兆候をいち早く捉える手段になる。

## 所感・ポイント

- 固定しきい値ではなく「そのアカウント自身の過去30日間のp95の2倍」かつ「組織全体のp99超え」という2軸の相対的な基準を採用している点が実務的である。人間とエージェントで利用パターンの性質（規則的か不規則か）が異なることを前提に設計されている点も、AI利用の異常検知として理にかなっている。
- 「コスト分析ツールは数多くあるが、そのアカウントの利用が“通常の範囲”かどうかを判断する機能は無い」という課題設定は、AI Gatewayが単なる課金・ログ収集ツールから一歩進んで、行動分析基盤へと進化していることを示している。
- Identity-aware AI Gatewayが確認済みユーザーIDをAI利用に紐付けるという発想は、[Cloudflare OS](2026-08-05-cloudflare-os.md)のGatekeeperが持つ「エージェントの参照履歴を記録し、それに基づいて以後のアクセスを制御する」という考え方とも共通しており、Cloudflareの一連の発表がゼロトラスト的な「常にIDと文脈を紐付ける」という一貫した設計思想でつながっていることがうかがえる。

> **Workers サンプル**: 対象外（Identity-aware認証連携とUser Insightsの異常検知はダッシュボード上の分析機能であり、Workersで動く再現可能な中心技術を持たないため）。
