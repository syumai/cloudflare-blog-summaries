## TL;DR

- Cloudflare の Workers AI は、データセンターに分散配置された GPU 上でオープンウェイトモデルの推論を提供している。本記事は Moonshot の **Kimi K シリーズ**と Z.ai の **GLM** という「大規模・長コンテキスト・Mixture-of-Experts」なモデルをどう効率よく大規模運用するかを扱う。
- 用いられている最適化手法は3つ: **KV キャッシュの量子化**、**モデル重みの圧縮**、**キャッシュ整合性の保護**。
- すべての実験はオープンソースの推論フレームワーク **SGLang** 上で行われている。
- KV キャッシュを BF16 から FP8 に量子化することで、Kimi K2.6 の対応コンテキスト長が約68.6万トークンから137万トークンへと倍増し、同時実行数64での スループットはBF16のピーク比で約41%向上、トークンあたりコストは約30%削減された。
- GLM 5.2 の重みを FP8 から INT4 に圧縮すると、チェックポイントサイズが705GBから421GBへと40%削減され、デコード時のスループットは同時実行数1で55%向上した。
- 量子化・圧縮によって同時実行数が大幅に上がった結果、数百リクエストが同じ物理 KV キャッシュページを共有するようになり、その整合性を守るためのタグベースの検証機構が導入された。オーバーヘッドはスループット変化 −0.38%〜−0.79%、p95 レイテンシ増加1%未満に抑えられている。

## 背景・課題

Kimi と GLM はいずれも「大規模・長コンテキスト・Mixture-of-Experts（MoE）」という共通の特徴を持つモデルであり、これはメモリ面で大きな課題をもたらす。長いコンテキストを扱うほど Attention 計算に必要な KV キャッシュは肥大化し、MoE モデルは活性化されるパラメータこそ一部でも、モデル全体の重みは GPU メモリに載せておく必要がある。

Cloudflare のように多数の顧客・多様なワークロードを単一の GPU フリートで捌く事業者にとっては、「同時に処理できるリクエスト数（同時実行数）」がそのままコストと応答性に直結する。そのため、精度をほとんど落とさずにメモリ使用量を削減し、同時実行数とスループットを引き上げる手法が求められていた。同時に、同時実行数が上がるほど、GPU上で共有されるメモリ資源（KVキャッシュのページ）を巡るバグや競合状態が実運用で顕在化しやすくなるという、新たな課題も生じる。

## 発表内容 / アーキテクチャ

### KV キャッシュの量子化

テキスト生成の過程で、モデルは既に処理したトークンの Attention 情報を保持する Key-Value（KV）キャッシュを維持する。このキャッシュのおかげで、会話が長くなってもコンテキスト全体を再計算せずに済む。デフォルトの16bit精度（BF16）フォーマットは多くのメモリを占有するが、8bit浮動小数点フォーマット（**FP8, e4m3**）に切り替えることでキャッシュサイズを半減できる。

Kimi K2.6 の場合、この変更により対応可能なコンテキスト長が約68.6万トークンから137万トークンへと倍増する。FP8への変換処理自体はトークンあたりのわずかな計算オーバーヘッドを追加するが、真のメリットは**同時実行数（concurrency）のキャパシティ**に現れる。

- BF16: 同時実行数1で137トークン/秒だが、同時実行数32でメモリ上限に達する
- FP8: 同時実行数64まで機能し、2,192トークン/秒を達成——BF16のピークと比べ約41%高速、トークンあたりコストは約30%削減

Prefill（プロンプト全体を処理する段階）と Decode（トークンを1つずつ生成する段階）を分離した「disaggregated prefill/decode」アーキテクチャにより、Prefill 段階は計算律速なので BF16 キャッシュを維持し、Decode 段階はメモリ制約がボトルネックになりやすいため FP8 を活用する、という使い分けが可能になる。複数のベンチマークで評価した結果、両フォーマット間の精度差は無視できるレベルだった。

### モデル重みの圧縮

GLM 5.2 の重み圧縮では、精度を8bit浮動小数点（FP8）から**4bit整数（INT4）**に落とすことで、チェックポイントサイズが705GBから421GBへと**40%削減**された。8-way テンソル並列構成での GPU あたりメモリ消費量は約88GBから約52GBに減少し、同じハードウェアで約118万トークン分のKVキャッシュを格納できるようになった。

トークン生成には GPU メモリからモデルの重みをストリーミングする必要があるため、データ量の削減はデコード性能を直接的に押し上げる。同時実行数1では、INT4 は FP8比で55%のスループット向上を示し、この効果は同時実行数が上がっても+21%〜+27%の幅で持続する。

一方でPrefillフェーズの挙動は異なる——INT4の重みは計算前に展開（expand）が必要なため、Prefillはむしろ遅くなる（INT4: 約8,660トークン/秒 に対し FP8: 約10,160トークン/秒）。ここでも disaggregated 設計が生き、Decode には得意な INT4 を、Prefill には優位な FP8 を、というように使い分けられる。ベンチマーク評価では、テストされたすべてのデータセットでINT4の精度はFP8モデルと比べて0.8ポイント以内に収まることが確認された。

### 共有 KV キャッシュの整合性保護

量子化と圧縮の両技術によって、単一 GPU 上で処理できるリクエストの同時実行数は大幅に向上する。これは裏を返せば、数百件のリクエストが**同じ物理 KV キャッシュページ**を同時に読み書きすることを意味する。この効率化こそが最適化の目的だが、同時に複雑さも増す——Paged Attention、Continuous Batching、キャッシュの再利用（reuse）はいずれも正確な帳簿管理（bookkeeping）を必要とする。Cloudflare のリクエスト量規模では、統計的には稀なエラーであっても日常的に顕在化してしまう。

KV キャッシュの整合性チェックの仕組みは単純である。各物理キャッシュページには、再割り当て（reallocation）のたびに更新される**タグ**が付与され、サーバー側はリクエストごとに「期待されるページ／タグの対応関係」を記録する。デコード処理がキャッシュにアクセスする前に、このマッピングが検証される。不一致が検出された場合は、誤ったデータを取得させるのではなく**リクエストを中断（abort）**する。

中規模の本番モデルで、入力8,192トークン・出力1,000トークンという条件で性能を計測したところ、オーバーヘッドはごくわずかだった。スループットの変化幅は−0.38%〜−0.79%、p95レイテンシの増加は1%未満に収まっている。実装は GPU カーネル融合（kernel fusion）を避けており（スレッドグループの競合状態を防ぐため）、代わりに検証は独立したバッチチェックとして行われる。整合性チェックを必要としない組織向けに、デフォルトではオーバーヘッドが計測不能なほど小さい no-op トラッカーが使われる。

### コード例について

本記事にはコード例は含まれていない。代わりに、KVキャッシュ量子化・重み圧縮・整合性保護それぞれの効果を裏付ける定量的な性能データ（スループット・レイテンシ・メモリ使用量・精度差）が中心的な内容になっている。上記「発表内容 / アーキテクチャ」の各節に、記事で示された具体的な数値をそのまま記載した。

## ユースケース

### 長コンテキストのエージェントワークロード

KVキャッシュのFP8量子化によって対応コンテキスト長が倍増するため、長い会話履歴やドキュメントを保持したまま推論を続ける必要があるAIエージェントのワークロードに直接的なメリットがある。

### 高同時実行数が求められるマルチテナント推論基盤

Cloudflare のように多数の顧客のリクエストを同一GPUフリートで処理する基盤にとって、同時実行数の向上（BF16の32から、FP8の64へ）はそのままコスト効率とスループットの改善に直結する。

### 精度を落とさずコストを抑えたい大規模モデル運用

GLM 5.2 のINT4圧縮のように、精度低下を0.8ポイント以内に抑えつつチェックポイントサイズとGPUメモリ消費を大きく削減できるため、大規模なオープンウェイトモデルを継続的に運用するコストを抑える手段として活用できる。

## 所感・ポイント

- 「Prefill は計算律速、Decode はメモリ律速」という特性の違いに着目し、disaggregated アーキテクチャの上でPrefillとDecodeそれぞれに異なる精度フォーマット（BF16/FP8、FP8/INT4）を使い分けている点が本記事の核心である。単純に「全部を低精度にする」のではなく、フェーズごとの特性に応じて最適なトレードオフを選んでいる。
- 同時実行数の向上がもたらす「共有KVキャッシュページの競合」という新たな運用リスクにまで踏み込み、タグベースの軽量な整合性チェック（オーバーヘッド1%未満）を導入している点は、最適化技術を実運用に投入する際のリアルな課題を示していて興味深い。
- コード例がない分、性能データの提示密度が高い記事であり、実際にモデルサービングの意思決定を行うエンジニアにとって参考になる数値（スループット・レイテンシ・精度差のパーセンテージ）が豊富に示されている。

> **Workers サンプル**: 対象外（GPUクラスタ上でのKVキャッシュ量子化・重み圧縮の最適化が中心で、Workersにデプロイして体験できる技術ではないため）
