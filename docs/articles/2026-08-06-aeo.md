# ランク付けから推奨へ：AIエージェント時代でサイトを成功に導く準備を整える

- 原文: [https://blog.cloudflare.com/ja-jp/aeo/](https://blog.cloudflare.com/ja-jp/aeo/)（英語版: [https://blog.cloudflare.com/aeo/](https://blog.cloudflare.com/aeo/)）

## TL;DR

- Cloudflareの集計では、HTMLページへのリクエストのうち人間によるものはすでに半数を下回っており、残りは機械（ボット・AIエージェントなど）からのアクセスになっている。
- 「見つけてもらう」ことの意味が、検索結果での上位表示から、AIエージェントに発見され・読み取られ・自信を持って推奨されることへとシフトしている。
- Cloudflareはこの変化に対応するため、サイトがエージェントから読み取り可能かを診断する**Agent Readiness / Diagnostics**をダッシュボードに統合し、新たに**Answer Engine Optimization（AEO）**機能を追加した。
- AEOは、AIアシスタント（現時点ではClaudeとGPT）が特定カテゴリの質問に答える際、自社サイトがどの程度引用・言及・推奨されているかを、Citation Rate・Prominence・Mention Rate・Share of Voiceという4指標で計測する。
- 計測はCloudflare AI Gatewayとカテゴリ単位の事前計算ベンチマークにより、都度モデルへ問い合わせることなく低遅延・低コストで提供される。

## 背景・課題

これまで「Webサイトに見つけてもらう」ことは、検索エンジンの検索結果ページでいかに上位表示されるか（SEO）という問題だった。しかし記事が指摘するのは、Webへのアクセス経路そのものが変わりつつあるという事実である。Cloudflareの計測によれば、HTMLページへの人間によるリクエストはすでに半数未満になっており、残りは何らかの機械によるアクセスが占めている。もちろんその全てが「人に代わって行動するAIエージェント」というわけではないが、その比率は急速に増加しているという。

この変化がサイト運営者に突きつける問題は二つある。一つは「自分のサイトはそもそもAIエージェントが利用できる作りになっているか」という技術的な疑問、もう一つは「AIアシスタントに質問したユーザーに対して、自社サイトがおすすめされる存在になっているか」というビジネス上の疑問である。従来、この二つを確かめる手段はほぼ存在しなかった。アクセスログを見てAIボットらしきUser-Agentのアクセス数を数えることはできても、そのボットが実際にサイトを使いこなせているのか、ユーザーへの回答の中で自社が推薦されているのかまでは分からない。チャットボットに個別に質問を投げて目視で確認するといった、場当たり的な方法に頼るしかなかった、というのが記事の問題提起である。

## 発表内容 / アーキテクチャ

### Diagnostics: 自分のサイトのエージェント対応状況を診断する

Diagnosticsは、既存の「Agent Readiness」に含まれる技術診断機能である。AIエージェントがサイトを読み取るのと同じ経路（robots.txt、サイトマップ、レスポンスヘッダー、コンテンツのMarkdown版、認証・利用可能なツールに関する公開メタデータなど）でサイトをスキャンし、エージェントがそもそもアクセスできるか、ページを発見できるか、機械可読な形式が用意されているかを確認する。結果は「Not Ready（未対応）」から「fully agent-native（エージェントに完全対応）」までの単一スコアとして表示され、個々のチェック項目はPass（合格）・Fail（不合格）・Neutral（及第点）で判定され、判定理由と実際に確認したリクエスト／レスポンスのエビデンスが添えられる。

![Diagnosticsの評価画面](https://blog.cloudflare.com/_emdash/api/media/file/01KZA2SCFCH4GV8MQGRGPKSRT4.png)
*図: Diagnosticsによるサイトのエージェント対応状況の評価画面（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/aeo/）*

チェック項目は難易度に応じて4段階に分類されている。

1. **Quick wins（即効性が高い）**: クローラーが読み取れるrobots.txt、XMLサイトマップ、AIクローラー向けルール、エージェント向けのクリーンなMarkdown提供設定など、多くのサイトで不足しがちだが対策効果の大きい基本項目。
2. **Technical groundwork（技術的基盤）**: Content Signals、APIカタログ、Linkヘッダー、AIエージェント向けログイン手順など。
3. **Advanced integration（高度な統合）**: OAuth Discovery、MCP（Model Context Protocol）やA2A（Agent2Agent）のエージェントカード、Skills Index、Web Bot Auth、WebMCPなど。
4. **Commerce**: AIエージェント向け決済の新標準（x402、ACP、UCP、AP2など）。現時点ではスコアには反映されず参考情報として表示されるのみ。

![チェック項目の4段階分類](https://blog.cloudflare.com/_emdash/api/media/file/01KZA2SCJRV8Y84DTKX4CRC06F.png)
*図: Quick wins/Technical groundwork/Advanced integration/Commerceの4段階分類（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/aeo/）*

改善が必要な項目には次のアクションが提示される。Cloudflareの機能（Markdown for Agents、Managed robots.txtなど）で対応できる場合は「Set up in Cloudflare」から設定画面へ直接遷移でき、それ以外の項目には、コーディングAIへ実装を依頼するためのプロンプトを生成する「Copy Agent Prompt」ボタンが用意されている。

### AEO: AIアシスタントから推奨されているかを計測する

DiagnosticsがWebサイトの「読み取りやすさ」を診断するのに対し、AEOタブが確認するのはその次の段階、すなわち「実際にAIに質問したとき、自社サイトが競合を差し置いて推奨されるか」である。検索順位のようにインプレッション数やクリック数のレポートが存在しないため、AIが競合サイトを紹介して自社が失注しても、それに気づく手段が今まで存在しなかった、という課題意識がここにも表れている。

![AEOタブの表示例](https://blog.cloudflare.com/_emdash/api/media/file/01KZA2SCHB021NKDSW68C9X8SR.png)
*図: AEOタブの指標表示例（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/aeo/）*

AEOはまずサイトの内容から業界・カテゴリ（例: 健康・フィットネス業界のスポーツウェアカテゴリ）を推測し、主要アシスタント（現時点ではAnthropicのClaudeとOpenAIのGPT）に対して、実際の顧客が投げかけそうな商品比較・おすすめ・一般的アドバイスといったプロンプトを送り、その応答を分析する。分析から得られる指標は次の4つ。

- **Citation Rate（引用率）**: カテゴリに関する回答のうち、情報源として自社サイトが引用された割合。
- **Prominence（突出度）**: 引用された場合に回答内容がどの程度自社サイトの情報に基づいているか、回答のどの段階で引用されているか。
- **Mention Rate（言及率）**: 情報源として引用されたかに関わらず、回答文中でブランド名（例: 「Cloudflare」）が言及された割合。Citation Rateと突き合わせることで「ブランド認知はあるが情報源としては引用されていない」というギャップを可視化できる。
- **Share of Voice（シェアオブボイス）**: 自社サイトと競合サイトの引用数の比率。どの質問で競合に負けているかを把握できる。

これらを算出するために、カテゴリ単位の**ベンチマーク**を事前に一度だけ作成し、同じカテゴリの全アカウントで共有する仕組みが採られている。ブランド名を指定せずカテゴリで想定される質問をAIに投げ、どのサイトがどの程度引用・言及されるかを記録しておくことで、(1) スキャンのたびにモデルへ問い合わせる必要がなく低遅延、(2) カテゴリ単位で問い合わせをまとめるため計算コストを削減、(3) 共通ベンチマークから「どのブランドが同じ文脈で語られやすいか」を分析し、自社が本来の競合と同じ市場のプレイヤーとしてAIに認識されているかを示す**Industry Fitスコア**を算出できる、という3つの利点が得られる。

![複数モデルへの問い合わせと評価の仕組み](https://blog.cloudflare.com/_emdash/api/media/file/01KZA2SCKJERT2KXC0AXWDZT8R.png)
*図: 複数のAIモデルへ同じ質問を複数回送り、回答を評価する仕組み（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/aeo/）*

AIアシスタントは同じ質問でも毎回同じ回答を返すとは限らないため、Cloudflare AI Gatewayを介して複数モデルに同じ質問を複数回投げ、そのばらつきを吸収する。評価対象は、自社が言及されたかだけでなく、情報源として引用されたか・回答のどの位置で引用されたか・回答内容がどの程度自社サイトを反映しているか、という点にまで及ぶ。人間の判断に近い評価はCloudflareのWorkers AIが自社インフラ上で処理し、モデル自身に自己採点させるのではなく厳密なテキスト解析も組み合わせることで、多数の回答を実用的な指標へ集約している。

さらに**AI Operator Activity**として、OpenAIやGoogleなどAI事業者ごとの実際のクローリング状況・送客状況も確認できる。どの事業者がコンテンツを読み取っているか、どの事業者が訪問者を送り返しているか、403（アクセス拒否）や404（リンク切れ）などクロール時のエラーも合わせて把握できる。記事では特に、大量にクロールしていながら訪問者を一切送り返さない事業者に注意すべきだと述べられている。

![AI Operator Activityの表示例](https://blog.cloudflare.com/_emdash/api/media/file/01KZA2SC8RB6YS1V3S3FQ1RS1P.png)
*図: AI事業者ごとのクロール状況・送客状況を示すAI Operator Activity（出典: Cloudflare Blog https://blog.cloudflare.com/ja-jp/aeo/）*

これらの指標はサイトごとに算出されるため、改善策を実施して再スキャンすることで、実際にビジネスに関わる質問に対して効果があったかを継続的に測定できる、という位置づけになっている。

## コード例

この記事はダッシュボード機能（Agent Readiness / Diagnostics / AEO）の紹介記事であり、コード例は掲載されていない。代わりに、記事内で言及されている技術要素・プロトコルを整理しておく。

- **Diagnostics（読み取りやすさの診断）が対象とする要素**: robots.txt、XMLサイトマップ、AIクローラー向けルール、Markdown版コンテンツ、Content Signals、APIカタログ、Linkヘッダー、OAuth Discovery、MCP（Model Context Protocol）／A2A（Agent2Agent）のエージェントカード、Skills Index、Web Bot Auth、WebMCP
- **Commerce関連の新標準（参考情報として表示、スコアには非反映）**: x402（HTTPステータスコード「402 Payment Required」の拡張仕様）、ACP（Agent Commerce Protocol）、UCP（Universal Commerce Protocol）、AP2（Agent Payments Protocol）
- **AEOの計測基盤**: Cloudflare AI Gateway（複数モデルへの問い合わせの抽象化）、Cloudflare Workers AI（回答の評価処理）

## ユースケース

### 自社サイトがAIエージェントに読み取れる状態かを確認する

Diagnosticsを使えば、robots.txtやサイトマップ、Markdown版コンテンツの有無といった基礎的な項目から、MCPやA2Aのエージェントカードのような高度な統合まで、段階的に自社サイトの「エージェントレディネス」を点検できる。Quick winsとして提示される項目から着手すれば、投資対効果の高い改善を優先しやすい。

### AIアシスタントの回答内で自社ブランドがどう扱われているかを把握する

「健康・フィットネス業界のスポーツウェアカテゴリ」のような自社の業種・カテゴリにおいて、ClaudeやGPTに実際の顧客が尋ねそうな質問（商品比較、おすすめ、一般的なアドバイスなど）を投げたときに、自社サイトが情報源として引用されているか、ブランド名だけが言及されているに留まっているかを、Citation RateとMention Rateの差から把握できる。

### 競合との比較でAIにおける存在感を測る

Share of VoiceやIndustry Fitスコアを用いれば、同じカテゴリの競合サイトと比べてAIの回答内でどの程度優位に立っているか、逆にどのような質問で競合に負けているかを定量的に確認できる。

### AI事業者ごとのクロール・送客のバランスを確認する

AI Operator Activityにより、どのAI事業者が自社コンテンツを大量にクロールしていながら訪問者を送り返していないか（コンテンツを消費するだけで送客がない状態）を確認し、robots.txtのルール調整など次のアクションを検討する材料にできる。

## 所感・ポイント

- この記事の核心は、「SEO」が「AEO」へと単純に名前を変えたわけではなく、評価すべき対象がページの検索順位から「AIの回答本文の中での扱われ方」へと質的に変わった、という点にある。インプレッションやクリックのように直接観測できない指標（引用位置・言及と引用の乖離・回答内での比重）を、複数モデルへの反復問い合わせとテキスト解析で近似しようとする設計思想は、他のAI可観測性の取り組みにも応用が利きそうである。
- カテゴリ単位でベンチマークを事前計算し全アカウントで共有するというアーキテクチャは、個々のサイトごとにリアルタイムでモデル問い合わせを行うコストとレイテンシーの問題を回避する実務的な工夫であり、同時に「同じカテゴリの他社と比較してどう見えているか」という相対評価（Industry Fitスコア）を自然に導出できる副次効果も持つ。
- Mention RateとCitation Rateを分けて計測している点は特に示唆的である。「AIに名前だけは知られているが、情報源としては信頼されていない」状態を可視化できるため、コンテンツ改善の優先順位づけに直結しやすい。
- Diagnosticsで言及されているMCP・A2A・Web Bot Auth・WebMCPといった要素は、Webサイト側がAIエージェントとの相互運用性を高めるための技術群として今後の関連記事もチェックしておく価値がある。

> **Workers サンプル**: 対象外（Diagnostics・AEOはCloudflareダッシュボード上の診断・計測機能であり、Workersで動く再現可能な中心技術を持たないため）。
