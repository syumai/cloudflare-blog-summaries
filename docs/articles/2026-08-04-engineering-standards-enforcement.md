## TL;DR

- 過去4か月間で、Cloudflareの**AIコードレビュアー**はエンジニアリング標準からの逸脱（記事では「violation」と呼ぶ）を約25万件検出し、1万6,000件のマージをブロックした。
- **spec reviewerエージェント**は、実装開始前の技術設計書600件近くを同じ標準に照らして評価してきた。
- この2つのシステムはいずれも、人間とエージェントの両方のために構築された共有のエンジニアリング指針**Cloudflare Codex**を参照している。
- Codex以前は、開発者向けガイダンスが正式ドキュメント・リポジトリ内ファイル・チャットの会話・個々のエンジニアの知識など、あちこちに散らばっていた。
- CodexはRFC形式で標準を管理し、`SHOULD`/`MUST`キーワード（RFC 2119）で要求レベルを表現する。承認（approved）と強制（enforced）というライフサイクルを分けることで、非ブロッキングの指摘とマージブロックを段階的に切り替えられる。
- AIコードレビュアー・spec reviewer・incident report reviewerという3つのエージェントがCodexを活用する具体例として紹介されている。

## 背景・課題

Codexが構築される以前、Cloudflareにおける開発者向けガイダンスは正式ドキュメント・リポジトリ内のファイル・チャットのスレッド・そして個々のエンジニアが蓄積してきた知識など、多くの場所に分散していた。エンジニアは、本来取り組むべき問題ではなく、ガイダンスを探すことそのものに多くの時間を費やしていた。ようやく答えを見つけたとしても、それが最新のものか、権威あるものか、自分の状況に本当に当てはまるのかを判断できないことも多かった。

Cloudflareが成長するにつれて、このモデルを維持するのは次第に難しくなっていった。どのエンジニアもすべての標準を読み切ることはできず、レビュアーもすべての要件を確実にチェックすることはできない。人がチームを異動するたびに組織としての知識を取り戻すのは難しくなり、一貫して周知・徹底されないガイダンスは、プロジェクト間の「ズレ（drift）」を生む原因になっていった。

Cloudflareはこの知識体系を**Cloudflare Codex**として再構築した。これは、エージェントが作業時点で取得・適用できる、統治された（governed）エンジニアリング標準の集合体である。同じガイダンスが、コードレビュー・技術設計レビュー・インシデントレポートレビューなど、さまざまなユースケースに活用できるようになり、エンジニアはガイダンス探しではなく、その結果得られた指摘内容に対する時間と判断力の行使に集中できるようになった。

## 発表内容 / アーキテクチャ

### Codexの組織構成とワークフロー

専用のCodexガバナンスモデルによって、Codexは関心領域ごとに明確なドメインへと分割されている。アーキテクチャに関わる領域（フロントエンド、コントロールプレーンなど）、横断的関心事（セキュリティ、信頼性）、特定の言語（TypeScript、Rust）、その他いくつかの領域が含まれる。各ドメインにはオーナーがおり、自分が担当する文書の内容・一貫性・全体的な品質に責任を持つ。

Codexの標準はRFC（Request for Comments）形式で記述される。要求事項にはRFC 2119で定義された `SHOULD` と `MUST` キーワードを使う。また、ドメインやRFCのステータスといったメタデータを保持するフロントマターヘッダーも必須とされる。強い関心とドメインの専門性を持つCloudflareの従業員であれば誰でも、規定された構造に従ったマージリクエストを通じてRFCを提案できる。その提案は、次第に幅広いレビュアーによる複数ラウンドのフィードバックを経る。ドメインオーナーの最終承認を得ると、RFCはCodexの一部となり、Astroで構築された社内サイトに公開される。

承認済み（approved）のRFCは、Codexのクライアントやエージェントがすぐに参照でき、コード・設定・ドキュメント内のCodex違反を即座に検出し始められる。しかし、実際にマージなどをブロックするのは、RFCがapprovedからenforced（強制）というライフサイクル状態に移行した後に限られる。この昇格ステップを別に設けることで、チームには新しい要件を消化する時間が与えられ、強制適用に追加の作業が必要なケースにも対応できる。

次の図は、Codexワークフローの各ステップを示している。承認済みRFCは非ブロッキングの指摘を生成し、明示的な昇格を経た強制適用RFCのみがMUST要件違反をブロックする、という流れである。

素朴なアプローチであれば、Codex全体をそのまま大規模言語モデル（LLM）に丸ごと渡して終わりにできたかもしれない。しかし、すでにRFCが60件以上あり、今も増え続けている現状では、そのコーパスの分量はコンテキストウィンドウに大きな負荷をかけ、LLMの結果にも悪影響を与えてしまう。そこでCloudflareは、モデルを最も関連性の高いRFCへ導くために、専用エージェントを使って `SHOULD` と `MUST` の文をJSON構造へ自動的に抽出・圧縮し、遅延発見（lazy discovery）と段階的開示（progressive disclosure）をサポートするメタデータで補強している。以下は、コントロールプレーンサービスに関するRFCに対するこの処理結果を抜粋したものである。

各ステートメントには、抽出処理中にRFCが更新されても変わらない安定した `slug` 識別子が付与される。この識別子によって、時間の経過とともに複数のシステムをまたいで同じステートメントを追跡できるようになり、モニタリング・分析・例外処理にとって不可欠な仕組みとなっている。

当初は、JSONではなくより簡潔なMarkdownファイルへ抽出していた。しかし時間の経過とともに、エージェントがより正確に必要な内容を絞り込めるよう、より構造化されたリッチな形式へと移行した。今後は、あるステートメントがSDLC（ソフトウェア開発ライフサイクル）のどの段階（設計・実装・実行時など）に適用されるかを示す指標など、さらに絞り込みを効かせるためのメタデータの追加も計画されている。

### Codexの利用者たち

すでにいくつかのシステムが、日々のエンジニアリング業務でCodexを活用している。Codexが実際にどう機能するかを示す例として、**AIコードレビュアー**・**spec reviewer**・**incident report reviewer**という3つのエージェントが紹介されている。

#### AIコードレビュアー

別のブログ記事でも取り上げられているAIコードレビュアーエージェントは、Codex準拠を含む複数の観点からマージリクエストを評価する。

レビューのたびに、このエージェントはRFCを取得しCodexのステートメントを解析する。RFCの本文全体を読み込むのは、モデルまたはコーディネーターが追加のコンテキストを必要とする場合のみである。ほとんどのケースでは、ステートメントだけで違反内容を説明するのに十分な情報が得られる。

`SHOULD` と `MUST` の区別、そしてRFCのステータス（approved/enforced）が、レビュアーの応答の仕方を決める。承認済みRFCからの指摘は非ブロッキングの推奨事項として扱われる。RFCがenforcedになると、満たされていないMUST要件は、深刻度に応じてレビュアーが承認を保留したり、マージリクエストをブロックしたりする原因になる。

Codex導入以来、AIコードレビュアーはこれまでに約23万件の違反を検出した。そのうち約1万6,000件は承認の保留を引き起こした（＝enforced状態のRFCにおけるMUSTステートメントに該当した）。

#### コードレビューの代替手段

AIコードレビュアーの1回の実行には、コーディネーターのフレームワークとサブエージェントの実行のため、通常数分かかる。この待ち時間はほとんどの場合それだけの価値（あるいはトークン消費）に見合うものだが、エンジニアからは、指摘を修正するまでの遅延と余分な往復についての声が上がっていた。Cloudflareはこの体験を改善する方法を検討し、次の2つの選択肢を追加した。

- 機械的に検証可能な言語固有のCodex要件については、**カスタムlinter設定パッケージ**を提供する。これはCodexの仕様に沿っており、問題をミリ秒単位で表面化できる。最初にCodex linterのサポートを受けたのはTypeScriptで、同時に高速なlinter実行のために（最近Cloudflareに参画したVoidZeroチームがメンテナンスする）**oxlint**を標準として採用した。Rustプロジェクト向けのlinterは開発中で、Cloudflareで最もよく使われる言語をカバーするため、いずれGoにも対応する予定である。
- CI（継続的インテグレーション）区間をレビューサイクルから省くため、AIコードレビュアーを**CLIでローカル実行**できるようにした。CIのコーディネーター機能と同じものを、自動的に決定された差分セットに対して同じ（OpenCodeベースの）エージェント群で実行し、結果をターミナルに表示する。

linterはほぼすべての開発者・コードベースにとって有用だと考えられている一方、CLIはそれを好むエンジニア向けの任意の代替手段という位置づけである。

#### spec reviewer

Cloudflareのエンジニアは、実装に着手する前に設計文書や技術仕様書（spec）を書くのが通例になっている。Codexのかなりの部分は、設計・アーキテクチャなど技術レビューに関連するテーマを扱っている。実装が始まる前にアーキテクチャ上のミスを発見するため、Cloudflareはspecを発見し、関連するCodex要件に照らして評価するエージェント「**spec reviewer**」を構築した。

spec reviewerはDeveloper Platform上で動作する。Cloudflare Workerとして実行され、結果と状態をD1に保存し、モデルへのリクエストはAI Gateway経由でルーティングし、Cron Triggerによって新しいspecのスキャンを開始する。まず、spec に関連するドメイン・セクションでCodexを絞り込む（たとえば、言語機能や実装寄りのRFCは対象外とする）。いくつかのガイド用プロンプトが、評価の実行方法と結果のまとめ方をモデルに指示する。得られた指摘は（SHOULD/MUSTキーワードに影響される）深刻度で評価され、一般的な品質やアーキテクチャに関する助言も含まれる。レビュー実行が完了すると、spec文書にはレビュー詳細を確認できる専用ダッシュボードへのリンクを含むノートが残される。

2026年5月以降、これまでに600件近いユニークなオープンspecがレビューされた。オンデマンドまたはspecの変更によってトリガーされた再実行も含めると、これまでに3,200件を超えるレビュー実行が記録されている。指摘の深刻度の大半は「major（重大）」（65%）または「minor（軽微）」（29%）で、「critical（致命的）」な指摘は少数派（6%）だった。

今後は、spec文書に直接コメントを投稿する形でより密接に統合すること、レビュー評価に影響を与えられる人間とエージェントの対話を埋め込むこと、影響度の高い提案には追加の人間によるレビューをフラグ付けすることが計画されている。

#### incident report reviewer

incident report reviewerは同じアプローチをインシデントレポート（ポストモーテム）に適用する。各レポートが完全かどうかをチェックするだけでなく、何が起きたのかを明確に説明しているか、要因を特定しているか、解決内容を文書化しているか、意味のあるフォローアップアクションを提案しているかを評価する。これらの期待値は、専用のCodex RFCで定義されている。

incident report reviewerは、spec reviewerと同じDeveloper Platformの構成要素（Worker・D1・AI Gateway・Cron Trigger）を使用している。この共通アーキテクチャは、CloudflareのCodexエージェントにおける一般的なパターンになりつつある。

2026年5月以降、このレビュアーは200件を超えるインシデントレポートを評価し、フォローアップアクション項目の欠落・不完全なタイムライン・検知シグナルの記載漏れといったギャップを特定してきた。それらのレポートのうち93%は、影響が小さい・社内限定・あるいは予防的に宣言されたインシデントを対象としたものだった。深刻度の高いインシデントについては、このレビュアーを包括的な中央レビュープロセスの必須ステップとしており、すべての指摘に対応するまでレポートは完了とみなされない。

### 今後の展望

CodexはすでにAIコードレビュアー・spec reviewer・incident report reviewerというエージェントを支えている。Cloudflareは、このモデルをSDLC全体に拡張し、設計・実装・運用にまたがって一貫して課題を表面化できるエージェント群を目指している。より長期的な目標は、エージェントが課題を発見するだけでなく、修正案を提案する自律性を段階的に高めていくことであり、その一方でエンジニアは変更のレビューと承認に責任を持ち続ける。

CloudflareはまたCodexをエンジニアリング以外にも拡張しつつある。プロダクト・セキュリティ・コンプライアンス・信頼と安全性を扱うチームが、それぞれ独自の標準をCodexに追加し始めており、エージェントが設計や実装だけにとどまらない観点から業務を評価できるようになりつつある。

## コード例

記事は主にプロセスとアーキテクチャの解説であり、実行可能なアプリケーションコードは含まれていないが、Codexの中核データ構造として、RFCから抽出されたステートメントのJSON表現が1件紹介されている。

### CodexステートメントのJSON構造（コントロールプレーンサービスRFCの抜粋）

```json
{
  "rfc": 14,
  "title": "Control Plane Services",
  "status": "approved",
  "domain": "control-plane",
  "statements": [
    {
      "slug": "use-quicksilver-for-edge-configuration-propagation",
      "section": ["Proposal", "Infrastructure"],
      "level": "SHOULD",
      "text": "If you need to propagate system or customer configuration to the edge, use Quicksilver via the outbox pattern",
      "href": "/rfcs/014-control-plane-services/#infrastructure"
    },
    {
      "slug": "api-schemas-must-be-documented-in-openapi-spec",
      "section": ["Proposal", "API Gateway"],
      "level": "MUST",
      "text": "API request and response schemas MUST be documented using an OpenAPI spec",
      "href": "/rfcs/014-control-plane-services/#api-gateway"
    }
  ]
}
```

**解説**: このJSONは、Markdownで書かれたRFC本文全体をエージェントに渡す代わりに、専用エージェントが `SHOULD`/`MUST` の要求文だけを抽出・圧縮した中間表現である。トップレベルの `rfc`・`title`・`status`（approved/enforced）・`domain` によって、このRFCがどのライフサイクル状態・ドメインに属するかが分かる。`statements` 配列の各要素は1つの要求事項に対応し、`level` が `SHOULD` か `MUST` かでレビュアーの対応（非ブロッキングの推奨か、強制時にマージをブロックしうる要件か）が変わる。`slug` はRFCが更新されても変わらない安定識別子で、同じ要求事項を時間をまたいで追跡するために使われる。`href` は元のRFC文書内の該当セクションへのリンクであり、AIコードレビュアーやspec reviewerが指摘の根拠を提示する際に利用できる。

## ユースケース

### AIコードレビュアーによるマージリクエストのCodex準拠チェック

マージリクエストのたびに、AIコードレビュアーがCodexのステートメントを参照し、`SHOULD`/`MUST` とRFCのライフサイクル状態（approved/enforced）に応じて非ブロッキングの推奨事項を出すか、マージそのものをブロックするかを判断する。過去4か月で約25万件の違反を検出し、1万6,000件のマージをブロックしている。

### 実装前の技術設計レビュー（spec reviewer）

エンジニアが書いた設計文書をspec reviewerが自動的に発見し、設計・アーキテクチャに関連するCodex要件に照らして評価する。実装に着手する前の段階でアーキテクチャ上のミスを検出できるため、後工程での手戻りを減らせる。2026年5月以降、600件近いユニークなspecが評価されている。

### インシデントレポート（ポストモーテム）の品質チェック

incident report reviewerが、インシデントレポートに要因・解決内容・フォローアップアクションが適切に記載されているかを自動的に評価する。深刻度の高いインシデントでは、このレビューが中央レビュープロセスの必須ステップとして組み込まれている。

## 所感・ポイント

- Codexの設計で興味深いのは、「approved（承認済み）」と「enforced（強制適用）」というライフサイクルを明確に分離している点である。新しい標準がいきなりマージをブロックするのではなく、まず非ブロッキングの指摘としてチームに周知され、後から明示的に「昇格」させて強制力を持たせるという段階的な導入プロセスが、大規模組織でのルール変更に伴う摩擦を和らげている。
- RFC全文をそのままLLMに渡さず、`SHOULD`/`MUST` の要求文だけを安定した `slug` 付きJSONへ圧縮するアプローチは、コンテキストウィンドウの制約に対する実務的な工夫として参考になる。60件を超えるRFC群を「そのまま」渡すのではなく、専用エージェントによる前処理レイヤーを挟むという設計判断は、社内ドキュメント全般をエージェントに読ませたい他の組織にも応用できそうである。
- AIコードレビュアー・spec reviewer・incident report reviewerの3エージェントがいずれも同じCodexとDeveloper Platformの構成要素（Worker・D1・AI Gateway・Cron Trigger）を土台にしている点は、社内向けエージェント基盤を「共通アーキテクチャパターン」として横展開している好例と言える。

> **Workers サンプル**: 対象外（AIコードレビュー・spec reviewer等の社内エンジニアリングプロセスの事例紹介であり、デプロイして体験できる単一のWorkers技術を持たないため）
