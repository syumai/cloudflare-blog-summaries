## TL;DR

- Cloudflare社内のAI活用の舞台裏を、CIOのSam Rhea氏が一人称で語る記事。同時発表の製品紹介記事「[Cloudflare OS：エージェント、アプリ、作業のためのオープンプラットフォーム](2026-08-05-cloudflare-os.md)」の背景・意思決定の経緯にあたる。
- 2025年末、モデルとツールの急速な進化により、社員から「AIで仕事のやり方を変えたい」という要望が殺到した。
- Cloudflareは「装備・有効化する責務」と「システム・データを安全に保つ責務」の両立のため、5つの基本原則を策定。
- エンジニア向け（Engineering Codex）と非エンジニア向け（「魔法のメールエイリアス」）の2つの並行パイロットを経て、ブラウザ完結型の**Cloudflare OS v1**を構築。
- さらに、都度AI推論を回すのではなく決定論的なコードとして自動化できる**Cloudflare OS v2**（エージェントによるワークフロー生成）へ進化させた。
- 直近1か月で営業チームだけで1万時間以上を削減、4,000を超えるアプリ・ツールが社員によって作成された。

## 背景・課題

記事は、営業組織のあるメンバーが「AIで“スーパーアプリ”を作ってgo-to-marketチームを変革したい」として、約12の本番システムへのアクセスとデプロイメントパイプラインへの管理者権限を求めてきた逸話から始まる。この要求の大きさが、当時Cloudflareが直面していた課題を象徴している。

Cloudflareは2025年を通じてAI導入には慎重な姿勢だった。社内向けの情報チャットボットや、ボイラープレートコード生成へのAI活用は試していたものの、「業務のやり方そのものを変える」段階には至っていないと判断していた。

しかし年末年始の数日間で状況が一変する。モデル性能とツールの改善により、AIエージェントが実際に「タスクをやり遂げる」ことができるようになった。技術・非技術を問わず数百人の社員が、年末年始の落ち着いた期間を使って新しいツールを試し、かつてないほど簡単にアプリやワークフローを構築できることに気づいた。その結果、「仕事のやり方を変えたい」という社員からの要望が一気に押し寄せた。

ここでCloudflareが向き合ったのが、「チームメンバーにAIツールを装備させ、有効に使わせる責務」と「社内システム・内部データ・顧客データを安全に保つ責務」という、一見相反する2つの責務だった。Cloudflare OSは、この2つを両立させるために数か月かけて構築されたプラットフォームである。既存のCloudflare WorkersやAccessなど開発者向け・Zero Trust向けの基盤コンポーネントを組み合わせるところから始まり、課題への理解が深まるにつれて、この新しい働き方専用のカスタムサービス（Gatekeeperなど）も追加していった。

## 発表内容 / アーキテクチャ

### 基本ルール（5つの原則）

CTOとSam Rhea氏がテキサス州オースティンのオフィスでAI導入方針の検討を開始し、組織全体のリーダーからフィードバックを募って以下の5原則を定めた。

1. **AIを使うためにAIを使わない**: まず「解決すべき仕事」（ペインポイント、ボトルネック、顧客体験向上の機会）を定義し、その後で適切なツールを選ぶ。
2. **全員が“超能力”を持つに値する**: AIツールの第一波は、開発者がすでに使っているコマンドラインなどのインターフェースに偏りがちで、非開発者を置き去りにする恐れがある。直感的なプラットフォームで、専門知識のない社員にも力を与えるべき。
3. **出力の所有者は人間である**: AIはあくまでツール（およびツールメーカー）であり、チームメンバーではない。品質・テスト・AI出力に依存するワークフローの定義責任は人間が負う。この原則はエージェントの運用にも及び、担当者が異動・退職した場合はマネージャーが他の業務同様にエージェントの責任を引き継ぐ。
4. **組織の文脈はモデルより重要**: Cloudflareで動くワークフローやエージェントは、Cloudflare固有の事情を理解している必要がある。そのためのキュレーションされた文脈層への投資が欠かせない。
5. **AI利用でアクセス権を拡張しない**: 社員は既存の製品・権限管理の仕組みによって、正当な理由でスコープされたデータビューしか持っていない。AIツールを使うときも、このアクセス範囲を超えてはならない。

### 2つの並行パイロット

**エンジニア向け: Engineering Codex** — AIツールはエンジニアの既存業務を加速させる一方、悪いコードもより速く書けてしまう。そこでCloudflareは、チームが従うべき原則・実践をまとめた権威あるガイド「Cloudflare Engineering Codex」を整備した。ポリシーが「してはいけないこと」を示すのに対し、Codexは「すべきこと」を明示する。コードベースの各領域には、その領域の品質に責任を持つドメイン所有者が存在する。このCodexはソフトウェア開発ライフサイクル全体で活用され、あるエージェントは作業計画をCodexに沿って支援し、別のエージェントはすべてのマージリクエストをCodex要件に照らしてレビューし、別のエージェントは実装前の技術設計を、さらに別のエージェントはインシデントレポートをレビューする。過去4か月間でこれらのエージェントは約250万件の潜在的な問題を検出し、16,000件のマージをブロック、約600件の設計でコードが書かれる前にアーキテクチャ上の問題を発見したという。

**非エンジニア向け: “魔法のメールエイリアス”** — 当初は非エンジニアにもエンジニア向けと同じツールを（多少親しみやすいUIで）提供したが、これは失敗だった。エンジニアはリポジトリをローカルにクローンし`AGENTS.md`のような文脈ファイルを追加してハーネスを動かせるが、非エンジニアの業務は「1回限りの成果物作成」や「何十ものシステムオブレコードにまたがる仕事」が中心で、市場にあるエンジニア向けハーネスとは相性が悪かった。そこでCloudflareは、社員が「自動化したいがやりたくない仕事」をメールで送れる「魔法のメールエイリアス」を用意した。裏側の小さなチームが数百、やがて数千件のセッションを処理する中で、社員が繰り返し依頼してくる定型業務のパターンを特定し、それをスキルファイルや文脈ファイルとして整備し、データ接続をマッピングし、期待される出力形式を定義していった。これにより、このメールエイリアス宛てのリクエストの一部を自動応答できるようになった。

### Cloudflare OS v1: ブラウザ完結のワークスペース

最初のプラットフォーム版は、Cloudflareのインフラ内のコンテナ上で動くシンプルなハーネスとして構成された。ユーザーはWebブラウザからアクセスし、Cloudflare Zero Trustで認証を受けたのち、「魔法のメール」フェーズで蓄積したスキルファイルやワークフローを実行できる。ローカル環境の構成は一切不要で、ラップトップを開けばすぐに作業を始められる。

Cloudflareは、クラウドベースのワークスペースにはユーザー体験以上の利点があると位置づけている。エフェメラルなクラウド環境は、そのセッションでユーザーが持ち込んだデータへのアクセスのみを持ち、セキュリティチームは監査可視性とネットワーク制御（インターネット上でどこに接続できるかのフィルタリングを含む）を確保できる。

**画像URL**: https://blog.cloudflare.com/_emdash/api/media/file/01KZ7KNN9369M9JEXJ7W2AGR0Z.png
*図: Cloudflare OS v1のランディングページ（出典: Cloudflare Blog https://blog.cloudflare.com/how-we-use-ai-with-cloudflare-os/）*

ユーザーが実行するスキルファイルは部門横断で識別された共通ワークフロー定義であり、会社が蓄積した文脈とノウハウをワンクリックで実行可能にする。画面右側のパネルには、技術アーキテクチャドキュメントやスライドデッキといったスキルファイルの出力がレンダリングされ、チームメイトと共有できる。

Cloudflare OSは、Model Context Protocol（MCP）Portalを通じてシステムオブレコード（SoR）に接続することでデータアクセスを実現している。MCPはAIツールをシステムオブレコードに接続する方法を定義する標準フレームワークで、AIツールに対して利用可能なデータと操作を示す。許可ルールに従い、Cloudflare OSのユーザーセッションのアクセス範囲は、対象システムに対する本人の既存の権限にスコープされる。多くの場合Cloudflareは、対象システムがネイティブのMCPサーバーを提供していても、あえて自前実装のMCPサーバーをCloudflare Workers上に構築・デプロイしている。これにより、ロールや地域単位のレート制限といった追加の制御層を独自に載せられるという。

**画像URL**: https://blog.cloudflare.com/_emdash/api/media/file/01KZ7KNNHBNVFCWA84C9DZH2FS.png
*図: MCP Portalを通じたシステムオブレコードとの接続（出典: Cloudflare Blog https://blog.cloudflare.com/how-we-use-ai-with-cloudflare-os/）*

さらに、Cloudflare OSが実行するAI推論はすべてAI Gatewayを経由してルーティングされる。これにより、ユーザーとAIシステム間のすべてのやり取りをフィルタリング・記録・監査できる。例えば、Secure Web GatewayのDLP（データ損失防止）ルールを再利用して、特定のデータセットが外部プロバイダーに送信されるのをブロックできる。AI Gatewayはまた「モデル利用の制御」機能も提供し、すべてのユーザーが最新フロンティアモデルの最大思考モードにアクセスする必要はないという発想のもと、ロール別にモデルをゲート制御したり、自動エージェント実行のような自動化ユースケースをより効率的なモデルに誘導したりできる。

**画像URL**: https://blog.cloudflare.com/_emdash/api/media/file/01KZ7KNNTTDXVRB6GPN1XPVADD.png
*図: AI Gatewayによる推論のフィルタリング・記録・監査（出典: Cloudflare Blog https://blog.cloudflare.com/how-we-use-ai-with-cloudflare-os/）*

### Cloudflare OS v2: 誰もが使えるエージェントで、より決定論的に

Cloudflare OS v1では、ユーザーがスキルファイルを実行するたびにトークン集約的な推論セッションが立ち上がっていた。しかしCloudflareが行う業務の多くは、実質的にはほぼ決定論的な一連のステップであり、適切な箇所にだけ推論（あるいは人間の判断）を挟めば十分である。「AIは常にツールである必要はなく、ツールメーカーであればよい」という発想のもと、CloudflareはCloudflare OSを更新し、ユーザーが自然言語でワークフローを説明すると、AIエージェントがそのワークフローを支えるコードを実際に生成し、オンデマンド・スケジュール実行・イベントトリガーのいずれかで動く仕組みへと進化させた。

この仕組みの権限管理を担うのが「gatekeeper」というサービスで、生成されたコードがデータセットへ安全に接続できるようにする（本記事と同時公開された製品紹介記事で詳述されているGatekeeperと同一の概念である）。

## ユースケース

### ITヘルプデスクの日次レポート作成（Sam Rhea氏自身の事例）

Sam Rhea氏が実際に関わるチームの一つが、Cloudflareの社内ITヘルプデスクである。ハードウェア・ソフトウェアに関する社員からの問い合わせを、古典的なチケットキューで管理している。氏は毎朝、未処理チケットのキューと、対応能力に関するメトリクスを確認したい。Cloudflare OS以前は、これを手作業で行っていた。チケットシステムには組み込みダッシュボードがあるもののかなり簡易的なため、CSVをダウンロードしてGoogle Sheetsに読み込み、チャートを作成し、さらにクローズ済みチケットを手動で1件ずつクリックして確認するという、時間のかかる作業で、システム外に冗長なデータのコピーも生んでいた。

**画像URL**: https://blog.cloudflare.com/_emdash/api/media/file/01KZ7KNNJ3NG9A98ZYVSZNKF36.png
*図: AIエージェントが生成するチケットキューの分析チャート例（出典: Cloudflare Blog https://blog.cloudflare.com/how-we-use-ai-with-cloudflare-os/）*

Cloudflare OS v1では、これをチケットシステムのMCPサーバーに接続したスキルファイルとして実行できるようになった。手作業は減り安全性も高まったが、その一方で、ほぼ毎朝内容が変わらない同じレポートを作るために、毎回数千トークンを消費していた（チケットのトリアージや返信ドラフトでも同様にトークンを消費していた）。

Cloudflare OS v2では、Sam Rhea氏が見たいチャートを説明すると、AIエージェントがそれを実現するコードを一度書き、`gatekeeper`経由でデータセットへの安全な接続を組み込む。以後は、毎朝レポートを読み込む際に消費するトークンは実質ゼロになる。さらに、AIによる推論が必要な場面（チケットへの返信ドラフト作成など）は、そのアプリの中に個別に埋め込むことができ、氏はドラフトをレビューして送信するだけでよい。統合やデプロイパイプラインを自前で構築・管理する必要は一切ない。氏が構築したこのアプリを他の同僚と共有した場合も、それぞれが自分自身の権限で認証され、同じ`gatekeeper`を通るため、データ境界を越えることはない。

**画像URL**: https://blog.cloudflare.com/_emdash/api/media/file/01KZ7KNNJMKFH9E6MDZY92DWW1.png
*図: チケットへのAI返信ドラフトの確認インターフェース（出典: Cloudflare Blog https://blog.cloudflare.com/how-we-use-ai-with-cloudflare-os/）*

### エンジニアリング領域: マージリクエスト・設計・インシデントの自動レビュー

Engineering Codexを参照するエージェントが、マージリクエストのレビュー、実装前の技術設計レビュー、インシデントレポートのレビューを担い、コードが書かれる前の段階で問題を検出する。

### 営業領域: 提案・テリトリー計画の自動化

営業チームのメンバーが、これまで手作業で行っていたテリトリー計画や提案書作成といったタスクをCloudflare OS上のアプリ・ワークフローに置き換えている。直近1か月だけで、営業チーム全体で1万時間以上の削減効果があったと見積もられている。

## 所感・ポイント

- 5原則のうち「AIを使うときにアクセス権を拡張しない」は、既存のゼロトラスト的な権限管理をAI時代にもそのまま適用するという、非常に実務的かつ一貫した発想である。AI導入にあたって新たな例外ルールを作らない、という姿勢が徹底されている。
- v1（都度推論を実行）からv2（推論結果をコードとして固定化し、以後は決定論的に実行）への進化は、AIエージェント活用における典型的なコスト最適化パターンとして参考になる。「毎回モデルに聞く」のではなく「一度モデルに“作らせて”、以降はコードとして再利用する」という考え方は、他の社内AI活用にも応用が利きそうである。
- 本記事は経営層（CIO）視点の「なぜ・どう意思決定したか」を描いており、同時公開の製品紹介記事「[Cloudflare OS：エージェント、アプリ、作業のためのオープンプラットフォーム](2026-08-05-cloudflare-os.md)」がアーキテクチャの技術的詳細（Gatekeeper、Dynamic Worker、Durable Object Facetなど）を担う、対になる構成になっている。両方を読むと理解が深まる。
