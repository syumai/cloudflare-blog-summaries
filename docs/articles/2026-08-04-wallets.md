## TL;DR

- AIエージェントは、人間向けに設計されたログインページの操作を強いられがちで、「安定したID」と「ネイティブな決済手段」の両方を持たないことが、エージェントによるソフトウェア利用開始（オンボーディング）や商取引の普及を妨げている。
- Cloudflareはこの課題に対し、**Cloudflare Wallets** を発表した。ユーザーは `cloudflare.pay` で一意のハンドルを取得でき、ステーブルコインの保管・サービスの購入・Web全体での資金受け取りが可能になる。
- 各アカウントは、利用条件（予算・許可する販売先・1回あたりの上限額など）を設定できる **Virtual Wallets** を作成し、エージェントに安全な範囲で資金を利用させられる。
- 決済だけでなく、`research.example.cloudflare.pay` のような人間が読めるエージェント識別子を通じて、エージェントが「誰の代理として動いているか」を検証可能にするデジタルアイデンティティの側面も持つ。
- 先月発表された **Monetization Gateway**（販売側の決済受け取り基盤）、Wallets（購入側の決済）、Identity（本人確認）の3要素が組み合わさることで、「ヘッドレスマーケットプレイス」の実現を目指すと位置づけられている。

## 背景・課題

記事はまず、AIエージェントが新しいAPIを試す際の障壁を指摘する。多くの場合、AIエージェントは人間向けに設計されたログインページを操作しなければならず、次の2点が課題として挙げられている。

- APIを利用開始するための安定した識別情報（ID）を持っていないこと
- APIの利用料金を支払うためのネイティブな決済手段を持っていないこと

この結果、「エージェントはソフトウェアの利用開始（オンボーディング）につまずくことが多く、エージェントによる商取引の普及が妨げられている」という状況が生じている。人間向けに最適化されたサインアップフローとクレジットカード決済という既存の仕組みは、そのままではエージェントの自律的な行動様式に合っていない、というのが本記事の出発点である。

## 発表内容 / アーキテクチャ

### Cloudflare Walletsの概要

Cloudflare Walletsは、ユーザーが `cloudflare.pay` でハンドルを取得できる仕組みとして紹介されている。このハンドルは、マーチャント（販売者）とのやり取りで利用できる一意のユーザー名として機能する。

記事では、先月発表された **Monetization Gateway** との関連も説明されている。Monetization GatewayはHTTPリクエストに決済情報を付加できる **x402プロトコル** を利用したマイクロペイメントに対応している。

### Cloudflare Walletsの機能詳細

Cloudflare Walletsは、ステーブルコインの保存・サービスの購入・Web全体での資金受け取りを可能にする仕組みである。各アカウントはVirtual Walletsを作成し、API・MCPツール・コンテンツなどを購入できるようになる。

Virtual Walletsでは、利用条件（利用可能な予算、利用を許可する販売先のリスト、1回あたりの最大利用金額など）を設定できる。これにより、エージェントによるアカウント資金の利用を安全に保ちながら、リスクを適切に管理し、多数のAPIを手軽に試すことが可能になる。

### エージェントコマース市場の両面を支える仕組み

エージェントコマースが成長するには、買い手側と売り手側の両方の仕組みが必要になる。Cloudflareの顧客はMonetization Gatewayを利用することで、コンテンツやAPIなどのリソースを、人手を介さずエージェント向けに販売できるようになる。

Cloudflare Walletsには2種類のウォレットが用意されている。

- **Account Wallet**: Cloudflareアカウントの所有者や利用者である人間向けのウォレット。ユーザーはウォレットへの入出金を行えるほか、エージェントが管理するVirtual Walletに利用可能な資金を割り当てることができる。
- **Virtual Wallet**: エージェント向けに設計されており、APIキーを介して操作する。エージェントは、Virtual Walletに設定された権限の範囲内で資金を利用できる。利用可能な金額には、Account Walletの所有者が設定した上限が適用されるため、それを超えて支出することはできない。

### 自由な試行

Virtual Walletの大きな魅力は、エージェントが本来得意とする「数十から数百ものサービスを試し、用途に最適なものを見つける」ことを実現できる点にある。利用上限をあらかじめ設定しておくことで、人間は安全な支出範囲を維持したまま、エージェントに自律的な判断を任せることができる。

具体例として、「従業員全員にAI推論用として週100ドルまで利用できる予算を設定したい場合は、必要な残高を設定したAccount Walletを用意し、そのルールを適用したVirtual Walletを各従業員向けに作成するだけです」という運用イメージが示されている。

ウォレットへの入出金については、まずは対応地域において法定通貨からの入金・出金（オンランプ／オフランプ）を簡単に行える仕組みを提供する予定であり、対象ユーザー向けにはステーブルコインによる直接の資金投入にも対応するとされている。

### 決済だけにとどまらない仕組み（デジタルアイデンティティ）

エージェントがマーチャントとやり取りする際、そのエージェントが誰の代理として動いているのかが必ずしも明確になるわけではない、という課題が指摘されている。

`cloudflare.pay` による識別子の提供によって、エージェントは必要に応じて自身のIDを提示できるようになる。例えば、ある調査用エージェントは `research.example.cloudflare.pay` のような識別子を持つことができ、マーチャントはそのエージェントが特定の組織に属することを確認できる。重要な点として、エージェントが自身のIDを公開するかどうかは完全に任意であり、既知のエージェントとの取引を優先するかどうかも各企業が判断できるとされている。

### エージェント識別子は人間が読める形であるべき

このセクションでは、エージェント対応が「VPNへの対応方法と似たもの」になっていくと予測されている。身元確認に関する既存の取り組みとして、CloudflareのTurnstile・Bot Management・Web Bot Authが言及されている。

Web Bot Authでは、すでにエージェントが鍵ペア（keypair）を使用して自身のIDを登録できるようになっている。Cloudflare Walletに紐付けられたIDは、この鍵ペアを人間が理解しやすい形式で表現できるようにするものであり、記事では「DNSにおけるURLとIPアドレスの関係」に似ていると比喩されている。「私たちが目指しているのは、IDを覚えやすくし、簡単に提示できるようにすることだけです」と述べられている。

### エージェントコマースの未来

最終セクションでは、Cloudflareの包括的な戦略として3つの構成要素が整理されている。

- **Monetization Gateway**: 販売者が従来の決済インフラを構築することなく、サービスやコンテンツの対価を受け取れる仕組み
- **Wallets**: エージェントを介して購入者が人手を介さずに支払いを行える仕組み
- **Identity**: マーチャントが身元を明らかにした購入者とやり取りしたり、必要に応じて本人確認を求めたりできる仕組み

これらすべての基盤要素が組み合わさることで、インターネット上に**ヘッドレスマーケットプレイス**が実現するとされている。

## コード例

記事内にアプリケーションコードの例は含まれていない。決済APIの具体的な呼び出し方法については、後述の関連リンク（x402互換のエンドポイントに関する開発者ドキュメント）を参照する必要がある。そのため本Wikiでは、記事内で説明されているVirtual Walletの利用条件（予算・許可販売先・上限額）の考え方を、設定イメージとして整理する。

```text
Account Wallet（人間の所有者）
  └─ 残高: 週次で補充される予算（例: 週100ドル）
      └─ Virtual Wallet（エージェント用、APIキーで操作）
           - 利用可能な予算: Account Walletの上限内
           - 許可する販売先のリスト
           - 1回あたりの最大利用金額
```

**解説**: 記事の説明を整理すると、Virtual Walletの権限設定は「予算」「許可リスト」「1回あたりの上限」という3つの軸で構成される。エージェントはこの範囲内でしか資金を動かせず、Account Walletの所有者が設定した上限を超えて支出することはできない。異常な支出速度など想定外の状況が発生した場合は人間が内容を確認し、意図した利用であれば上限を引き上げたり追加資金を投入したりできる、という運用フローになっている。

## ユースケース

### APIの試用・比較

x402によるステーブルコインのマイクロペイメントを利用すれば、アカウントを作成しなくてもAPIを簡単に試せるようになり、エージェントは手間をかけることなく、さまざまなAPIを試して比較できるようになる。

### 従業員向けのAI利用予算管理

「従業員全員にAI推論用として週100ドルまで利用できる予算を設定したい場合は、必要な残高を設定したAccount Walletを用意し、そのルールを適用したVirtual Walletを各従業員向けに作成するだけです」という運用が挙げられている。組織内でのエージェント利用コストの分配・管理をウォレット単位で行える。

### エージェントIDの公開によるマーチャント側の信頼判断

`research.example.cloudflare.pay` のような識別子を持つ調査用エージェントの例のように、エージェントが自身の所属組織を明示することで、マーチャント側は「特定の組織に属するエージェントであること」を確認した上で取引できる。

### 異常検知と対応

想定以上の速度で支出が増えるなど異常な状況が発生した場合には、人間が内容を確認し、意図した利用かどうかを判断できる。意図した支出であれば、Account Walletの管理者は利用上限を引き上げたり、一時的に追加資金を投入したりできる。

## 所感・ポイント

- 「ID」と「決済手段」という2つの欠落を同時に扱っている点が本記事の特徴で、単なる決済機能の追加ではなく、Web Bot AuthやTurnstileといった既存のボット識別技術とウォレットを結びつけている構成は、エージェント経済の基盤を一体で設計しようとする姿勢の表れといえる。
- Account WalletとVirtual Walletという「人間の資金プール」と「エージェントの利用枠」を分離する設計は、[エージェント開発ライフサイクル](./2026-08-04-agent-development-lifecycle.md)で述べられていた「許可制（段階的に権限を拡大できる仕組み）」という要件と考え方が共通しており、Agents Week全体を通じた「エージェントに権限を与えるが、無制限には与えない」という思想の決済版と位置づけられる。
- `research.example.cloudflare.pay` のような人間可読な識別子を「DNSにおけるURLとIPアドレスの関係」になぞらえている説明は分かりやすく、エージェントの身元確認という抽象的な課題を、既存のインターネットの仕組みに接続して理解させる工夫だと感じる。
- 一方で、記事にはAPIの具体的な呼び出しコードやSDKの使用例が含まれておらず、実装レベルの詳細は開発者ドキュメント（x402互換エンドポイントなど）に委ねられている。実際に組み込む際は、そちらを参照しての追加調査が必要になる。

> **Workers サンプル**: 対象外（Cloudflare Walletsは決済・資産管理サービスで、記事内にAPI呼び出しコード例が無く、実アカウント・実資金の準備なしには最小実装を再現できないため）
