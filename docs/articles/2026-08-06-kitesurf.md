# Kitesurfのご紹介 — Cloudflare Workers上で動く、エージェントファーストのブラウザ

- 原文: [https://blog.cloudflare.com/kitesurf/](https://blog.cloudflare.com/kitesurf/)（日本語版なし）
- 公開日: 2026-08-06

![記事ヘッダー画像](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8A48BKM6KQG36DQEWN7V.png)

## TL;DR

- Cloudflareは、AIエージェント専用に設計された新しいブラウザ **Kitesurf** を発表した。Chromiumなどの既存ブラウザエンジンを使わず、**Cloudflare Workers上で完全に動作する**点が最大の特徴。
- Chromiumのようなブラウザは人間向けに作られており、タブ・テーマ・拡張機能・デバイス間同期などAIエージェントには不要な機能のオーバーヘッドを抱えている。Kitesurfはそれらを削ぎ落とし、トークン数・コンテキストウィンドウ・スケーラビリティ・コストといったAIエージェントにとって重要な観点に最適化されている。
- 内部はRust実装をWebAssemblyにコンパイルして構築されており、HTML/CSSパースには `Blitz`（モジュール式レンダリングエンジン）と `Stylo`（FirefoxのCSSパーサー）、`eval` の実行には `Boa JS`（Rust製のECMAScriptエンジン）を利用している。
- スクリーンショット取得・HTML抽出といった典型的なエージェント向けタスクにおいて、Chromiumに比べてCPU・メモリ消費量が3〜7倍少ない（体感速度＝壁時計時間は1.7〜1.8倍ほどChromiumより遅い）。
- Web Platform Tests（WPT）を21万5,000件以上通過しており、毎週数百件のペースで通過数を伸ばしている。Browser Run上で無料ベータとして今日から試すことができる。

## 背景・課題

Cloudflareは「自分たちでブラウザを作るべきか」という問いに社内で何年も向き合ってきたという。記事はまず、ブラウザが「インターネットのOS」とも言えるほど重要なソフトウェアであることを確認したうえで、AIエージェントの普及によって状況が変わったと指摘する。

最大の課題は、ChromiumのようなブラウザエンジンはあくまでGUIを持つ人間の利用者向けに設計されているという点にある。タブ管理、テーマ、拡張機能、デバイス間同期といった機能は、AIエージェントにとっては一切不要でありながら、メモリと計算資源を大きく消費する。エージェント1体につき専用のブラウザインスタンスを1つ割り当てるようなモデルでは、このオーバーヘッドのコストが割に合わなくなる。

さらに、AIエージェントがブラウザを使う際の脅威モデルも人間の利用とは異なる。プロンプトインジェクションやツールの安全性といった、人間向けブラウザではあまり意識されてこなかった問題が、エージェント向けブラウザでは最優先の検討事項になる。記事は「人間にしか役立たない機能を犠牲にしてでも、AIモデルにとって重要なことに秀でたブラウザを、すべてのエージェントに提供すべきだ」という立場を明確にしている。視覚的な完璧さや滑らかな60fpsスクロールより、構造化された機械可読なコンテンツの方が重要だという価値観の転換が、Kitesurf開発の出発点になっている。

## 発表内容 / アーキテクチャ

### 開発の経緯

Kitesurfは、AI自動化向けのRust製ヘッドレスエンジンである `obscura`（"no Chrome, no Node.js, no dependencies" を掲げるプロジェクト）からインスピレーションを得て始まった。AIエージェントの力を借りてこれをCloudflare Workers上へ移植する試みは最初はうまく動かなかったが、AIに明確な計画と「成功の定義」を与え、エージェントが自律的にループしながら必要な確認を行えるようにしたところ、動作するプロトタイプが生まれたという。このプロトタイプに手応えを得て、チームとして本格的に開発を進めることになった。

### 設計上の意思決定

記事では、プロトタイプから実運用に耐えるブラウザへと仕上げていく過程で採用した5つの設計方針が語られている。

- **テストを何よりも重視する**: AIによる開発速度を落とさずに品質を担保する手段として、Web Platform Tests（WPT）を活用した。WPTはW3C標準への準拠を測る大規模なテストスイートであり、AIエージェントに明確な達成目標を与えられる。ただしWPTは実際のWebサイトを描画・操作する能力までは測れないため、これを補うためにPuppeteerを使った統合テスト・ビジュアルリグレッションテストも実装し、Chromiumとの出力差分を毎ステップ比較している。
- **可能な限りRustを使う**: Cloudflare WorkersはWebAssembly（Wasm）を長く支援しており、高性能なC/C++/RustパッケージをWasmにコンパイルして利用できる。Kitesurfでは、不要なエミュレーション層を挟まずに `wasm-bindgen` を使ってRustをそのままWasmへコンパイルする方針を採った。
- **例外処理を徹底する**: ブラウザは信頼できない、時に悪意あるコンテンツを含むWeb全体を、セッションを落とさずに描画し続けなければならない。「どんな失敗も、空白のフレームや欠落した要素への劣化にとどめ、セッションを絶対に殺さない」というルールをあらかじめ決め、あらゆる境界で例外を捕捉し、安全なデフォルトにフォールバックし、診断に足るログを残す設計にしている。
- **分離（Isolation）を徹底する**: 人間が使うブラウザとは異なり、エージェントはタスクが要求する任意のオリジンの、任意のコードにアクセスする。そのためKitesurfは「すべてのページロードは信頼できない入力であり、すべてのセッションはゼロから始まる」という前提で設計されている。Cloudflare Workersのセキュリティモデルはアイソレート同士の分離を土台にしているが、それだけでは不十分で、各コンポーネントがどのリソースに触れてよいかをアプリケーションレベルでも厳密に制御している。
- **可能な限りステートレスにする**: 状態を持たないコンポーネントは使い捨てにでき、並列実行がしやすい。クラッシュしても新しいインスタンスを起動してリクエストをリプレイするだけで復旧できる。バースト的に負荷がかかる自動化ワークロードにはこの性質が非常に相性がよく、「ステートレスにできる箇所はすべてステートレスにする」という方針が採られている。

### リクエストのライフサイクルと4つのコンポーネント

Kitesurfは、1件のページ描画リクエストを次の4つのコンポーネントで処理する。

![高レベルのリクエストライフサイクル](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8A7NX68CP9DHW93JAHJX.png)
*図: Kitesurfにおけるリクエストの高レベルなライフサイクル。Engine・PageScript・PageRendererが連携して1つのページを描画する（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

**1. SandboxOutbound（origin取得の唯一の窓口）**

信頼できないWebページを描画するには、画像・フォント・CSS・JavaScript・Wasmファイルなど任意のアセットをインターネットから取得する必要があり、これはブラウザの中でも特に危険な操作である。Kitesurfでは、ネットワークに直接触れられるコンポーネントを `SandboxOutbound` という単一のWorkerに限定し、それをDynamic Workersによって強制している。EngineはメインドキュメントとスクリプトのブートストラップにSandboxOutboundを使い、PageScriptはスタイルシート・画像・フォント・ページ自身の `fetch()` 呼び出しなど、それ以外すべての取得に使う。SandboxOutboundはCORSの強制、ブラウザらしいヘッダーの付与、レスポンスのフィルタリング、ページごとのクッキーの隔離（cookieを個別の「jar」で管理）を担っており、ポリシーに反するリクエストは403で拒否される。

![SandboxOutboundのアーキテクチャ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8AAR723T5KJCNQ547FAV.png)
*図: SandboxOutboundを介したネットワークアクセスの仕組み（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

**2. Engine（唯一の外部公開コンポーネント）**

EngineはKitesurfで唯一、外部に公開されるコンポーネントである。Chrome DevTools Protocol（CDP）のWebSocketおよびHTTP REST APIを処理し、内部テスト用のランディングページを提供し、何より各セッションの状態を保持する（他のコンポーネントはすべてステートレス）。CDPを採用したことで、Puppeteer・Playwright・chrome-remote-interface・Chrome DevToolsのフロントエンドなど、既存のクライアントがそのままKitesurfに接続できるという互換性上の利点が生まれている。名前に反して、Engine自体はKitesurfの構成要素の中では比較的シンプルな部類だという。

![Engineのアーキテクチャ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8AHPEVW2VZK1VM59SZHW.png)
*図: Engineコンポーネントの構成（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

**3. PageScript（DOMとJavaScriptの実行）**

PageScriptは、Cloudflareの新しいWorkers機能である**Dynamic Workers**の威力を示す好例であり、記事は「Kitesurfはこの機能なしには実現できなかった」と述べている。新しいページ、あるいはout-of-process iframe（OOPIF）ごとに、Dynamic Workersを使って長寿命のPageScriptアイソレートを起動し、クリーンな `globalThis` とDOMドキュメントオブジェクトを持つページセッションを管理する。HTML/CSSのパースにはRust製の `Blitz`（モジュール式レンダリングエンジン）と `Stylo`（FirefoxのCSSパーサー）を利用し、見つかった `<script>` タグや `.wasm` ファイルは同じアイソレート内でJavaScript/WebAssemblyとして実行される。

`eval` への対応は特に工夫が必要だった箇所である。セキュリティ上の理由からWorkersはネイティブの `eval` をまだサポートしておらず、かといって別のアイソレートを新たに起動しても `globalThis` へのアクセスができない。Kitesurfでは、Rust製のECMAScriptエンジンである `Boa JS` をコンパイルしてWorkers上で動かし、いわば「ランタイムの上でランタイムを動かす」形でこの問題を解決している。最適な構成ではないと認めつつも、実用上十分に機能するとし、将来Workersにネイティブの `eval` サポートが入り次第、Boaからの移行を予定しているという。

![PageScriptの内部アーキテクチャ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8A7714HEP695P6HKY8GD.png)
*図: PageScriptの内部構成。Dynamic Workersごとにページセッションを分離する（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

**4. PageRenderer（ピクセルの生成）**

PageRendererは、計算済みのページオブジェクトから実際のピクセルを生成する役割を担う。EngineがフレームをリクエストするたびにPageRendererはPageScriptからページオブジェクト（"scene" と呼ばれる）を取得し、Static Assetsから内部フォントと画像を取得したうえで画像バッファへラスタライズし、クライアントが表示できる形式（JPEG/PNG/PDF）でEngineに返す。このラスタライズには、`Blitz` のもう一つのモジュールである `blitz-paint` が使われており、文字のシェイピングやフォント選択、テキストの改行処理には `Parley` が使われている。

![PageRendererの描画ループ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8AR04KBNA79NHBQYG562.png)
*図: EngineとPageRendererが連携するレンダリングループ（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

Kitesurfは、EngineとPageRendererの通信にCloudflare Workersの組み込みRPC機構を使っている。API仕様や型、認証を意識せずに `remoteFunction(...params)` を呼ぶだけで、リモートWorkerの隔離性とリソースを享受しながらローカルなJavaScript呼び出しのような利便性が得られる。EngineはPageRendererの `renderFrame()` を1回のRPC呼び出しで叩き、結果としてPNGを受け取る。PageRendererはページの状態を（使い捨てのキャッシュ以外）一切保持していないため、失敗したり応答が止まったりしたRPC呼び出しがあれば、Engineはいつでも安全にPageRendererを終了・再起動できる。この「レンダリング要求はそれ自体で完結し、再試行可能で、アイソレートは安価に使い捨てられる」という性質が、システム全体のレジリエンスを支えている。

### WPTテストと性能ベンチマーク

Kitesurfは、Web Platform Tests（WPT）を**21万5,000件以上**通過しており、毎週数百件のペースで通過数を伸ばしている。CSS・DOM・HTML・selection・SVG・XHRなど、エージェントにとって重要な領域はすでに手厚くカバーされており、streamsのようにエージェント用途では優先度が低そうな領域でも、それなりのサポートが実現されているという。

![WPTテスト通過数の推移](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8A1TZBWVWDT3XZQR7AB1.png)
*図: WPTテスト通過数が時間とともに伸びている様子（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

![カテゴリ別のテストカバレッジ](https://blog.cloudflare.com/_emdash/api/media/file/01KZ9Z8AF7AB8HWYJJ0DZCRK5X.png)
*図: CSS・DOM・HTML・SVG・XHRなどカテゴリ別のテスト通過状況（出典: Cloudflare Blog https://blog.cloudflare.com/kitesurf/）*

性能面では、Chromium（ウォームプール）との比較として以下の数値が示されている。

| 指標 | Kitesurf | Chromium（ウォームプール） | Kitesurfの相対値 |
| --- | --- | --- | --- |
| CPU: スクリーンショット | 380 ms | 1,173 ms | Chromiumの約3.1分の1のCPU |
| CPU: HTML抽出 | 229 ms | 877 ms | Chromiumの約3.8分の1 |
| メモリ: スクリーンショット | 57.8 MiB | 271.0 MiB | Chromiumの約4.7分の1 |
| メモリ: HTML抽出 | 39.4 MiB | 273.7 MiB | Chromiumの約7.0分の1 |
| 壁時計時間: スクリーンショット | 1,148 ms | 637 ms | Chromiumの約1.8倍遅い |
| 壁時計時間: HTML抽出 | 820 ms | 472 ms | Chromiumの約1.7倍遅い |

記事は「すでにそのページを見たことがあるJITは、コールドな状態のソフトウェアレンダラーに常に勝る」として、壁時計時間ではChromiumが約1.7倍速いことを認めつつ、そのギャップの多くはラスタライズとJPEG/PNGエンコード処理に起因しており今後も最適化を続けるとしている。一方で、実際に課金対象となるメモリとCPUについてはKitesurfがChromiumの3〜7倍効率的であり、より多くのセッションを同時に走らせられ、スケーラビリティとコストの両面で優位に立てるとまとめている。

余談として、記事は「テストをどれだけ積んでも、Doomが動かなければプロジェクトは真に完成したとは言えない」として、[silentspacemarine.com](https://silentspacemarine.com/) をKitesurf上で動かした例（過去のDoom Multiplayer on Workers実験に絡めたもの）を紹介している。

### Browser Runでの利用開始

KitesurfはBrowser Run経由で今日から無料ベータとして試すことができる（アカウントごとの利用制限あり）。Browser RunのCDPエンドポイントは新たにKitesurfをオプションとしてサポートしており、既存のPuppeteer・Playwright・chrome-remote-interfaceクライアントや、MCPとCDPを話すAIエージェントは、エンドポイントに `browser=kitesurf` パラメータを追加するだけでそのまま動作する。

DevTools付きの公開プレイグラウンド（Kitesurf Playground）も用意されており、任意のURLを入力してKitesurfでの描画結果を確認したり、UI内に組み込まれたChrome DevToolsでDOM要素の検査・コンソールメッセージの確認・ネットワークアクティビティの監視を行える。特にMemoryパネル向けに必要なCDP命令を実装しており、各アイソレートが消費するWebAssemblyのフットプリント（フレーム含む）を確認できるようになっている。

## コード例

記事には2つのコード例が掲載されている。いずれもKitesurfをBrowser Run経由で使い始めるための設定例である。

### 例1: MCPクライアントからKitesurfへ接続する（CDP）

```json
{
  "mcp": {
    "kitesurf": {
      "type": "local",
      "command": [
        "npx",
        "-y",
        "chrome-devtools-mcp@latest",
        "--wsEndpoint=wss://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/browser-run/devtools/browser?browser=kitesurf",
        "--wsHeaders={\"Authorization\":\"Bearer <API_TOKEN>\"}"
      ],
      "enabled": true
    }
  }
}
```

**解説**: MCPクライアント（記事の例ではOpencode向け設定）の設定ファイルに、`chrome-devtools-mcp` をローカルコマンドとして登録する例。`--wsEndpoint` のクエリパラメータに `browser=kitesurf` を付けるだけで、通常はChromiumに接続するCDPクライアントの接続先をKitesurfに切り替えられる。認証は `--wsHeaders` に渡す `Authorization: Bearer <API_TOKEN>` ヘッダーで行う。既存のCDP対応ツールをそのまま流用できる、という記事の主張（Puppeteer・Playwright・chrome-remote-interfaceなどが「そのまま動く」）を体現する設定例になっている。

### 例2: Browser Run Quick Actionsでスクリーンショットを取得する

```bash
curl -X POST 'https://api.cloudflare.com/client/v4/accounts/<accountId>/browser-run/screenshot?browser=kitesurf' \
  -H 'Authorization: Bearer <apiToken>' \
  -H 'Content-Type: application/json' \
  -d '{
    "url": "https://example.com"
  }' \
  --output "screenshot.png"
```

**解説**: Browser RunのQuick Actions（スクリーンショット取得用のREST API）を、`browser=kitesurf` パラメータ付きで叩く例。CDPセッションを自前で組み立てる必要がなく、URLをJSONボディに指定するだけで対象ページのスクリーンショットPNGを取得できる。CDPによるインタラクティブな操作だけでなく、こうした一発完結型のAPI呼び出しでもKitesurfを選択できることを示している。

## ユースケース

### エージェントによるページ描画・情報抽出

Kitesurfは、完全機能でピクセルパーフェクトなChromiumブラウザを使わないことのトレードオフを許容できる、AIエージェント向けのページ描画に適している。TodoMVC（vanilla・React・Vue・Angular・Preact）、Wikipedia、Hacker News、Cloudflareブログ、Cloudflareダッシュボードの大部分など、すでに正しく描画できるサイトが例として挙げられている。

### スクリーンショット・PDF生成・コンテンツ抽出などの一発完結タスク

Quick Actionsに代表される「1回のAPI呼び出しでページからコンテンツを抽出する」「スクリーンショットやPDFを生成する」といった一発完結型の自動化・アプリケーションとの相性が特に良いとされている。記事は「Kitesurfは、タスクの実行時間だけ存在するために設計された、一時的で完全に分離されたステートレスなエンジンであり、バースト的でAI駆動のワークロードに対してよくスケールする」とまとめている。

### （現時点では非対応）動画再生・WebGL・ボット対策突破・長時間の認証セッション

記事は逆に、Kitesurfがまだ得意ではない領域も明記している。動画再生、WebGLレンダリング、実TLSフィンガープリントを使ったボットチャレンジの突破、永続的な状態を要する10分規模の認証済みセッションが必要な場合には、Kitesurfではなく（Chromiumで動く）Browser Runの通常構成を使うべきだとしている。あるサイトがKitesurfと互換性があるかどうかを確かめる一番確実な方法は、実際にAPIかプレイグラウンドで試してみることだと述べられている。

## 所感・ポイント

- 「ブラウザをもう1つ作る」のではなく、「ブラウザが最適化すべき対象を人間からAIエージェントへ根本的に置き換える」という発想が本記事の核心だと感じる。タブや同期機能を削ぎ落とし、CPU・メモリという「実際に課金される指標」に最適化する姿勢は、コンテナ中心の実行環境から一歩進んだ設計思想として読める。
- CDP互換性を維持したまま独自実装に置き換えるという判断は、既存のPuppeteer/Playwright/MCPエコシステムをそのまま活かせる点で実務上のインパクトが大きい。`browser=kitesurf` というクエリパラメータ1つで切り替えられる手軽さは、既存ワークフローへの導入障壁を大きく下げている。
- Rust実装をWasmにそのままコンパイルする方針（Blitz・Stylo・Boa JSの組み合わせ）は、「ブラウザエンジンをゼロから作る」のではなく「実績のあるRustエコシステムのコンポーネントを組み合わせる」アプローチであり、12週間という短期間で21万5,000件超のWPTテストを通過できた背景にありそうだ。
- ステートレス設計（PageRendererを含む各コンポーネントを気軽に殺して再起動できる）と、EngineだけがセッションStateを持つという役割分担は、障害復旧の単純さとスケーラビリティを両立させるための、非常に実践的な設計判断だと感じる。
- 壁時計時間はChromiumに劣るという正直な数値開示（1.7〜1.8倍遅い）をしたうえで、CPU・メモリという別の軸で3〜7倍の優位性を主張する構成は、性能評価を一面的にせず読者の判断材料を厚くしている点で好感が持てる。

> **Workers サンプル**: [examples/kitesurf/](../../examples/kitesurf/) — Browser Run の Quick Actions API を `browser=kitesurf` で呼び出し、スクリーンショットを取得するプロキシWorker。
