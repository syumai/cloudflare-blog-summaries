## TL;DR

- MCP（Model Context Protocol）のツールをLLMに直接「ツール呼び出し」させるのではなく、ツール群をTypeScript APIに変換し、LLMにそのAPIを呼び出す「コード」を書かせてサンドボックス内で実行する方式「Code Mode」を提案している。
- 理由はモデルの学習データの偏りにある。ツール呼び出しの特殊トークン形式は合成的な訓練データでしか出てこないが、実世界のTypeScriptコードは大量に学習済みで、LLMはコードを書く方がずっと得意。
- 複数のツールを連鎖させるタスクも、コードとして書けば1回の実行にまとめられる。中間結果をいちいちLLMのニューラルネットワークに通す必要がなくなり、トークン・時間・エネルギーを節約できる。
- 実装はCloudflare Agents SDKの `codemode` ヘルパー。MCPのスキーマからTypeScript APIを自動生成し、生成されたコードはDynamic Worker Loading（Worker Loader API）で作る使い捨てのV8アイソレート内で実行される。インターネットアクセスは遮断され、MCPサーバーへはbinding経由でのみアクセスできる。
- MCP自体を否定しているわけではない。「ツールへの統一的な接続・認可・ドキュメント提供」というMCPの価値は残しつつ、LLMにツールを使わせる最後の一歩（呼び出し方法）だけをコードに置き換える、という立場。

## 背景・課題

MCP（Model Context Protocol）は、AIエージェントに外部ツールへのアクセスを与えるための標準プロトコルとして広く使われるようになった。しかし記事は、その使い方——LLMに「ツール呼び出し」という特殊な形式でツールを使わせるやり方そのもの——に問題があると指摘する。

典型的なツール呼び出しは、`<|tool_call|>` のような特殊トークンに囲まれたJSONをLLMが生成し、その結果を `<|tool_result|>` として受け取る、というやり取りを1ツール1往復ずつ繰り返す形になる。この形式は、LLMの訓練データの中でどれだけ出現しているだろうか。実世界のコードは無数に存在するが、この特定のツール呼び出しフォーマットは、合成的に作られた訓練データにしか存在しない。記事はこれを、シェイクスピアに1ヶ月の中国語講座を受けさせてから中国語で戯曲を書かせるようなものだ、とたとえている。能力はあっても、不慣れな言語で表現させられているという比喩である。

この記事は、「MCPというプロトコル自体は有用なのに、LLMにそれを使わせる方法（ツール呼び出し）が非効率だ」という課題に対して、Cloudflareが提案する解決策をまとめたものである。

## 発表内容 / アーキテクチャ

### MCPとは何か

MCPは、AIエージェントに外部ツールへの統一的なアクセスを与えるための標準プロトコルである。ツールの接続方法・認可（認証）・ドキュメントの提供方法を標準化することで、エージェント開発者が個別のAPIごとに接続方法を作り込む必要をなくしている。この「統一性」こそがMCPの本質的な価値だと記事は位置づけている。

### ツール呼び出しの解剖

MCPでツールを使う典型的なやり取りは、LLMが `<|tool_call|>` のような特殊トークンでツール名と引数のJSONを出力し、ツール実行結果を `<|tool_result|>` として受け取る、というプロトコルに従う。これを複数ツール分、1往復ずつ繰り返していく。

### 何が問題か

この形式には2つの弱点がある。1つ目は、LLMがこの特殊なトークン形式を訓練データの中でほとんど見たことがない点（実世界のコードに比べて合成データが極端に少ない）。2つ目は、複数ツールを連鎖させるタスクでは、あるツールの結果を次のツールの入力に使うために、その都度LLMのニューラルネットワークを介して結果を受け渡す必要があり、無駄なトークン・時間・計算資源を消費してしまう点である。

### それでもMCPは統一性という価値がある

記事はMCPを否定するのではなく、「統一的な接続・認可・ドキュメント」という価値は維持すべきだと明言している。問題があるのはツール呼び出しという「最後の一歩」の実装方法であり、MCPというプロトコル自体を置き換える必要はない、という立場である。

### 仕組み: MCPをTypeScriptに変換する

Code Modeの核心は、MCPツールのスキーマから、対応するTypeScript APIの型定義を自動生成することにある。LLMは個別のツール呼び出しではなく、生成されたTypeScript APIを呼び出す「コード」を書く。LLMは大量の実世界のTypeScriptコードで訓練されているため、こちらの方が本来得意な形式でタスクを表現できる。

### サンドボックスでコードを実行する

LLMが書いたコードは、そのまま実行されるわけではなく、サンドボックス内で安全に実行される。

### Dynamic Worker Loading: コンテナ不要

このサンドボックスは、コンテナではなく「Dynamic Worker Loading」という仕組みで実現されている。生成されたコードは、その場で作られる使い捨てのV8アイソレートの中で実行される。コンテナに比べてアイソレートはミリ秒単位で起動し、消費メモリも数MB程度と軽量である。

### Worker Loader API

Dynamic Worker LoadingはWorker Loader APIというCloudflare Workersのバインディングとして提供される。`env.LOADER.get(id, callback)` の形で呼び出し、コールバックが返すオブジェクトで、動的に作るWorkerのコード（`mainModule` / `modules`）・環境変数やバインディング（`env`）・アウトバウンド通信の制御（`globalOutbound`）を指定する。

サンドボックス内のコードからMCPサーバーへアクセスする際は、bindingを経由する。bindingは文字列（URLやAPIキー）ではなく「ライブオブジェクト」として渡されるため、APIキーそのものがサンドボックス内のコードに渡ることはない。これはネットワークフィルタでアクセスを制限するよりも明確な権限境界になる、と記事は説明している。

### Workersはより良いサンドボックス

コンテナベースのサンドボックスと比べて、V8アイソレートを使うWorkerのサンドボックスは起動が速く、リソース消費が小さい。この特性が、LLMが生成したコードをリクエストのたびに使い捨てで実行する、というCode Modeのユースケースに向いている。

Worker Loader APIは、本稿執筆時点で本番環境ではクローズドベータ（サインアップ制）として提供されている。ローカル環境（`wrangler` / `workerd`）では現在でも試すことができる。

## コード例

### 1. 従来のai-sdkでのツール定義

```javascript
const stream = streamText({
  model: openai("gpt-5"),
  system: "You are a helpful assistant",
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ],
  tools: {
    // tool definitions 
  }
})
```

**解説**: `ai-sdk` を使った通常のツール呼び出しの実装。`tools` にツール定義を渡すと、LLMはこれらを個別に「ツール呼び出し」として呼び出す。

### 2. `codemode()` ヘルパーでラップする例

```javascript
import { codemode } from "agents/codemode/ai";

const {system, tools} = codemode({
  system: "You are a helpful assistant",
  tools: {
    // tool definitions 
  },
  // ...config
})

const stream = streamText({
  model: openai("gpt-5"),
  system,
  tools,
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ]
})
```

**解説**: Cloudflare Agents SDKが提供する `codemode()` ヘルパーの使い方。既存の `ai-sdk` 用の `system` と `tools` をそのまま渡すだけで、Code Mode対応の `system` と `tools` に変換してくれる。呼び出し側のコード（`streamText` への渡し方）はほとんど変わらない点がポイントで、既存のツール定義を書き換えずにCode Modeへ移行できることを示している。

### 3. ツール呼び出しの特殊トークン形式（従来方式）

```
I will use the Weather MCP server to find out the weather in Austin, TX.

<|tool_call|>
{
  "name": "get_current_weather",
  "arguments": {
    "location": "Austin, TX, USA"
  }
}
<|end_tool_call|>
```

```
<|tool_result|>
{
  "location": "Austin, TX, USA",
  "temperature": 93,
  "unit": "fahrenheit",
  "conditions": "sunny"
}
<|end_tool_result|>
```

**解説**: 従来のツール呼び出しがどのような形式でLLMとやり取りされるかを示す例。`<|tool_call|>` や `<|tool_result|>` は、モデルの訓練時に定義された特殊トークンで、この形式自体が実世界のコードに比べて訓練データ中に乏しい、という記事の指摘の根拠になっている。

### 4. MCPスキーマから自動生成されたTypeScript API

```typescript
interface SearchAgentsCodeInput {
  /**
   * The search query to find relevant code files
   */
  query: string;
  /**
   * Page number to retrieve (starting from 1). Each page contains 30
   * results.
   */
  page?: number;
}
interface SearchAgentsCodeOutput {
  [key: string]: any;
}

declare const codemode: {
  /**
   * Fetch entire documentation file from GitHub repository:
   * cloudflare/agents. Useful for general questions. Always call
   * this tool first if asked about cloudflare/agents.
   */
  fetch_agents_documentation: (
    input: FetchAgentsDocumentationInput
  ) => Promise<FetchAgentsDocumentationOutput>;

  /**
   * Semantically search within the fetched documentation from
   * GitHub repository: cloudflare/agents. Useful for specific queries.
   */
  search_agents_documentation: (
    input: SearchAgentsDocumentationInput
  ) => Promise<SearchAgentsDocumentationOutput>;

  /**
   * Search for code within the GitHub repository: "cloudflare/agents"
   * using the GitHub Search API (exact match). Returns matching files
   * for you to query further if relevant.
   */
  search_agents_code: (
    input: SearchAgentsCodeInput
  ) => Promise<SearchAgentsCodeOutput>;

  /**
   * Generic tool to fetch content from any absolute URL, respecting
   * robots.txt rules. Use this to retrieve referenced urls (absolute
   * urls) that were mentioned in previously fetched documentation.
   */
  fetch_generic_url_content: (
    input: FetchGenericUrlContentInput
  ) => Promise<FetchGenericUrlContentOutput>;
};
```

**解説**: 実際にAgentsドキュメント用のMCPサーバー（`gitmcp.io/cloudflare/agents`）のツール定義から自動生成されたTypeScript API定義の例。各ツールが `declare const codemode` の中のメソッドとして、入力・出力の型付きの関数として表現されている。LLMは、この型定義に対して「呼び出すコード」を書けばよく、JSDocコメントに書かれた説明文がそのままツールの使い方のドキュメントとして機能する。

### 5. Worker Loader APIの使用例

```javascript
// Gets the Worker with the given ID, creating it if no such Worker exists yet.
let worker = env.LOADER.get(id, async () => {
  // If the Worker does not already exist, this callback is invoked to fetch
  // its code.

  return {
    compatibilityDate: "2025-06-01",

    // Specify the worker's code (module files).
    mainModule: "foo.js",
    modules: {
      "foo.js":
        "export default {\n" +
        "  fetch(req, env, ctx) { return new Response('Hello'); }\n" +
        "}\n",
    },

    // Specify the dynamic Worker's environment (`env`).
    env: {
      // It can contain basic serializable data types...
      SOME_NUMBER: 123,

      // ... and bindings back to the parent worker's exported RPC
      // interfaces, using the new `ctx.exports` loopback bindings API.
      SOME_RPC_BINDING: ctx.exports.MyBindingImpl({props})
    },

    // Redirect the Worker's `fetch()` and `connect()` to proxy through
    // the parent worker, to monitor or filter all Internet access. You
    // can also block Internet access completely by passing `null`.
    globalOutbound: ctx.exports.OutboundProxy({props}),
  };
});

// Now you can get the Worker's entrypoint and send requests to it.
let defaultEntrypoint = worker.getEntrypoint();
await defaultEntrypoint.fetch("http://example.com");

// You can get non-default entrypoints as well, and specify the
// `ctx.props` value to be delivered to the entrypoint.
let someEntrypoint = worker.getEntrypoint("SomeEntrypointClass", {
  props: {someProp: 123}
});
```

**解説**: サンドボックスとなる使い捨てWorkerを動的に生成する、Worker Loader APIの基本的な使い方。`env.LOADER.get(id, callback)` にIDとコールバックを渡すと、既存のWorkerがあればそれを返し、無ければコールバックの返り値（`mainModule` / `modules` / `env` / `globalOutbound` などを含むオブジェクト）を元に新しいWorkerを作る。`env` には `ctx.exports` を使って親Worker側のRPCインターフェースをバインディングとして渡せる。`globalOutbound` に親Workerを指定すると、動的Workerからのすべてのアウトバウンド通信（`fetch` や `connect`）を親側でフィルタ・監視でき、`null` を渡せばインターネットアクセスを完全に遮断できる。生成後は `worker.getEntrypoint()` でエントリポイントを取得し、通常のWorkerと同じように呼び出せる。

## ユースケース

### 多数のツール・複雑なツールを扱うエージェント

Code Modeを使うと、エージェントが扱えるツールの数や複雑さが実質的に増える。個々のツール呼び出しを特殊トークンで表現する必要がなく、慣れたプログラミング言語（TypeScript）としてツールの組み合わせを表現できるため、より複雑なタスクの遂行にも対応しやすくなる。

### 複数ツールを連鎖させるタスク

あるツールの出力を次のツールの入力に使うようなタスクでは、コードとして1回の実行にまとめることで、中間結果をLLMに逐一戻す必要がなくなる。トークン消費・レイテンシ・計算コストの削減につながる。

### 既存のMCPサーバー・ai-sdkプロジェクトへの適用

`codemode()` ヘルパーは既存の `ai-sdk` のツール定義をラップするだけで使えるため、すでにMCP・ツール呼び出しを使って構築されているエージェントに対しても、大きな書き換えなしにCode Modeを導入できる。

## 所感・ポイント

- 「MCPは良いプロトコルだが、ツール呼び出しという最後の一歩の実装が悪い」という切り分け方が、この記事の主張を分かりやすくしている。プロトコルとしての統一性・認可・ドキュメント提供という価値は維持しつつ、LLMに不慣れな形式で作業させている部分だけをコードに置き換える、という提案である。
- シェイクスピアの比喩は、LLMの能力とその発揮のさせ方のミスマッチをうまく言い表している。ツール呼び出しができないのではなく、慣れない形式で無理にやらせているために効率が落ちている、という指摘は納得しやすい。
- この記事で紹介されているCode Modeは、この後 [コードモード: エージェントに1,000トークンのAPI全体を提供](2026-02-20-code-mode-mcp.md) で紹介される「サーバー側コードモード」の土台になっている。あちらの記事では、クライアント側でコードを実行する方式（この記事の方式）に加えて、CLI型・動的ツール検索・サーバー側コードモードという4つのアプローチが比較されており、合わせて読むと位置づけがつかみやすい。
- 実行基盤であるWorker Loader APIは、本稿執筆時点で本番環境ではクローズドベータ（サインアップ制）として提供されている。ローカル環境（`wrangler` / `workerd`）では試すことができる。

> **Workers サンプル**: 対象外。中心技術であるWorker Loader API（Dynamic Worker Loading）は本番環境ではクローズドベータ（サインアップ制）のため、デプロイ可能なサンプルは作成していません（ローカルの `wrangler dev` では試せます）。
