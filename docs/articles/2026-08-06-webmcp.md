# あらゆるWebサイトにWebMCPインターフェースを付与する

- 原文: [https://blog.cloudflare.com/webmcp/](https://blog.cloudflare.com/webmcp/)（日本語版なし）
- 公開日: 2026-08-06

![ヘッダー画像](https://blog.cloudflare.com/_emdash/api/media/file/01KZBCD42EV16T4QX44FMGRZ1E.png)
*図: 記事ヘッダー画像（出典: Cloudflare Blog https://blog.cloudflare.com/webmcp/）*

## TL;DR

- Cloudflareは、任意のWebサイトにAIエージェント向けの「ツール」インターフェースを付与する developer preview 版 **WebMCP** を発表した。
- WebMCPは、Chrome 146で実験的に提供されるブラウザ標準で、ページ上に `document.modelContext` として現れ、サイトが自身の「ツール」一式をAIエージェントに公開できるようにする仕組み。
- Cloudflareの実装は、サイトのオリジンコードを一切変更せず（"no code and nothing changed at your origin"）、エッジ側でHTML配信時に小さなブリッジスクリプトを1行注入するだけで有効化できる。
- 初回プレビューでは「Content Credentials（C2PA画像の来歴確認）」と「Site MCP Server（サイト自身のMCPサーバーへのプロキシ）」という2つの「ツールパック」が提供される。
- 登録されるツールはMCP（Model Context Protocol）の `Tool` / `CallToolResult` 型に準拠しているため、既存のMCPクライアント／エージェントは特別な対応をせずにこのページ上のツールを呼び出せる。

## 背景・課題

これまでのWebは、人間が読む・クリックする・フォームに入力するという操作を前提に作られてきた。しかし近年は、AIエージェントがWebサイトを「訪問」してタスクを代行するケースが急増している。従来型のクローラーは、ページのHTMLをスクレイピングしてサーバー側にコンテンツをコピーするアプローチを取るため、元のサイト運営者にはトラフィックもクレジット（帰属）もほとんど還元されない。加えて、エージェントはページ構造やナビゲーションの流れを自力で推測してから操作を組み立てる必要があり、これは遅く、壊れやすく、無駄なトークン消費（推測・試行錯誤）を生む。

つまり課題は二重で、(1) サイト運営者からすると「エージェント経由の訪問」を制御・可視化する手段がない、(2) エージェント開発者からすると「サイトを操作するためのAPI」が事実上存在せず、UIをスクレイピング・推測して操作するしかない、という状態だった。この記事はこの2つの課題に対して、サイト側の実装コストをほぼゼロにしたまま解決を図るアプローチを提示している。

## 発表内容 / アーキテクチャ

### WebMCPという新しいブラウザ標準

WebMCPは、Chrome 146で実験的に搭載される新しいブラウザ標準であり、ページ上で `document.modelContext` として公開される。サイトはこのインターフェースを通じて「ツール」のセットをエージェントに公開でき、エージェントはページのナビゲーションを推測する代わりに、公開されたツールを直接呼び出せるようになる。これにより、エージェントが消費するトークンは「ページ構造の推測」ではなく「本来のタスク遂行」に振り向けられるようになる、という位置づけである。

### Cloudflareの実装戦略: ツールパック

Cloudflareの developer preview は「ツールパック（tool pack）」という単位で機能を提供する。ツールパックとは、関連するツール群をひとまとめにしたものであり、サイト運営者はダッシュボードで新しいパックを有効化するだけで機能を拡張でき、再デプロイは不要である。今回のプレビューでは以下の2つのパックが含まれる。いずれも完全にブラウザ内（訪問者のブラウザ）で実行される。

- **Content Credentials パック**: C2PA（Content Authenticity and Provenance Association）の来歴情報を画像から読み取るツール群。
- **Site MCP Server パック**: サイト自身が持つMCPサーバー（`/mcp` エンドポイントなど）を発見し、そのツールをブラウザ上のツールとしてプロキシするツール群。

### 実装の2要素: Edge injection と Bridge

Cloudflareの実装は大きく2つの要素から成る。

**1. Edge injection（エッジでの注入）**

CloudflareはHTMLRewriterを用いて、配信するすべてのHTMLレスポンスに1行のスクリプトタグを注入する。オリジン側のコードやHTMLそのものは一切変更されない。

```html
<!-- Cloudflare injects this at the edge. Same origin, and your HTML is otherwise untouched. -->
<script type="module"
        src="/.webmcp/bridge.js"
        data-packs="c2pa,mcp-server-client"
        data-mcp-url="/mcp"></script>
```

`data-packs` 属性には有効化するパック名をカンマ区切りで指定する。すでに自前のMCPサーバーを持っているサイトであれば、`data-mcp-url` 属性でそのエンドポイントを指定できる（未指定時は同一オリジンの `/mcp` がデフォルトとして使われる）。

**2. The bridge（ブリッジスクリプト）**

注入された `bridge.js` はページ内で実行され、ブラウザにWebMCPサーフェス（`document.modelContext`）があるかを確認する。存在しない場合は何もせず終了する（＝ブラウザが対応していなければ完全に無害）。対応している場合は、`data-packs` で指定されたパックを1つのツールリストにまとめ、`.registerTool()` を使って各ツールを登録する。

- **静的パック**（例: Content Credentials）は、あらかじめ定義済みのツールをそのまま宣言する。
- **動的パック**（例: Site MCP Server）は、起動時にサイト自身のMCPサーバーへ問い合わせ、そこで公開されているツールを発見してから登録する。

登録後、すべてのツールは訪問者自身のブラウザ内で実行される。Content Credentialsパックは画像を取得してメタデータをローカルで解析し、Site MCP Serverパックはページ側から訪問者自身のオリジン（＝そのサイト自体）にあるMCPサーバーへ通信を行う（訪問者のセッション・Cookieを使う点がポイント）。

ブリッジのコード自体はCloudflareのエッジ上で動作するWorkerが配信しており、記事では「将来的なパックはこのWorkerを呼び出して、サイト単独ではできないタスク（サイトマップの要約生成やAI Searchインデックスの参照など）を行える」という発展の方向性にも言及されている。

### MCP標準との関係

Site MCP Serverパックが登録するツールは、MCP（Model Context Protocol）の `Tool` 型・`CallToolResult` 型にそのまま準拠する。つまりブリッジは「サイト自身のMCPサーバーへのブラウザ内プロキシ」として機能しており、既存のMCPサーバーと通信できるエージェントであれば、特別な追加対応なしにこのページ上のツールを呼び出せる。

### Content Credentials パックの詳細

C2PA準拠の画像（生成AIツールや編集ソフトウェアが埋め込む来歴メタデータを持つ画像）を対象に、2つのツールを提供する。

- `scan_images_c2pa`: ページ内の全画像をスキャンし、各画像についてC2PAメタデータの有無・件数・要約（生成に使われたツール名、タイトル、署名者など）をまとめて返す。
- `inspect_image_c2pa`: 単一画像を対象に、編集履歴・作者情報・署名証明書を含む完全なマニフェストをデコードして返す。TypeScript製のリーダーが画像先頭の数キロバイトのみを読み取る軽量実装で、現時点では認証情報の「報告」のみを行い、暗号学的な署名検証は行わない（レスポンスには常に `signatureVerified: false` が含まれる）。

### 有効化方法（Try it out）

サイト運営者は Cloudflare Dashboard の「Agent Readiness > WebMCP」セクションからドメインを選び、有効化するパックを選択する（Content CredentialsとSite MCP Serverはデフォルトで有効）。有効化後は次のコマンドで注入されたスクリプトタグの存在を確認できる。

```bash
curl -s https://your-site.example | grep webmcp
```

動作確認には、Cloudflareのリモートブラウザサービスである BrowserRun を使うことができる。BrowserRunは既にWebMCPに対応しており、ラップトップ上のブラウザまたはクラウド上のヘッドレスブラウザのいずれでも同じ方法でツールの動作を検証できる。今後は Cloudflare Radar も自身のWebMCPツールを提供していく予定であるとされている。

## コード例

記事には4つのコード例が示されている。すべて原文（英語）のまま引用する。

### エッジでの注入スクリプト（HTML）

```html
<!-- Cloudflare injects this at the edge. Same origin, and your HTML is otherwise untouched. -->
<script type="module"
        src="/.webmcp/bridge.js"
        data-packs="c2pa,mcp-server-client"
        data-mcp-url="/mcp"></script>
```

**解説**: HTMLRewriterによってすべてのHTMLレスポンスの末尾（あるいは適切な位置）に自動挿入される1行。`type="module"` のスクリプトタグとして `/.webmcp/bridge.js`（同一オリジン）を読み込み、`data-packs` 属性で有効化するツールパック名をカンマ区切りで指定し、`data-mcp-url` 属性で（既存のMCPサーバーがあれば）そのエンドポイントを指定する。オリジンのHTMLはこの1行が足されるだけで、他は一切変更されない。

### MCP Tool Proxy（JavaScript）

```javascript
// For each tool the site's own MCP server advertises (via tools/list),
// registering a proxy whose execute() calls the site back on the
// visitor's origin, with their session.
document.modelContext.registerTool({
  name: tool.name,                 // e.g. "search_products"
  description: tool.description,
  inputSchema: tool.inputSchema,   // taken straight from tools/list
  execute: async (args) => {
    const res = await fetch(mcpUrl, {   // same-origin /mcp
      method: "POST",
      credentials: "same-origin",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({
        jsonrpc: "2.0", id: 1, method: "tools/call",
        params: { name: tool.name, arguments: args },
      }),
    });
    const { result } = await res.json();
    return result;   // an MCP CallToolResult, passed straight through
  },
});
```

**解説**: これが「Site MCP Server」パックの中核実装である。サイト自身のMCPサーバーが `tools/list` で公開しているツールそれぞれについて、ブラウザ側の `document.modelContext.registerTool()` を使ってプロキシ用のツールを登録している。`execute()` の中身は、標準のMCP JSON-RPCリクエスト（`method: "tools/call"`）を、訪問者自身のブラウザから `credentials: "same-origin"` 付きで `/mcp` エンドポイントに投げているだけである。つまりエージェントから見えるツール呼び出しは、実際には「訪問者本人のセッション・Cookieを使ってサイト自身のMCPサーバーを叩く」形で実行される。レスポンスの `result`（MCPの `CallToolResult`）はそのままエージェント側に返される。

### `scan_images_c2pa` の実行結果例（JSON）

```json
{
  "imageCount": 12,
  "scanned": 12,
  "withC2pa": 8,
  "results": [
    {
      "src": "https://example.com/hero.jpg",
      "hasC2pa": true,
      "format": "image/jpeg",
      "manifestCount": 1,
      "claimGenerator": "Adobe Firefly",
      "title": "sunrise over the bay",
      "signedBy": "Adobe Inc."
    },
    { "src": "https://example.com/logo.png", "hasC2pa": false, "format": "image/png" }
  ]
}
```

**解説**: ページ内の画像12枚をスキャンし、うち8枚にC2PAメタデータが含まれていたという結果。`hasC2pa: true` の画像には、生成・編集に使われたツール（`claimGenerator`）、タイトル、署名者（`signedBy`）などのメタデータが付与される。`hasC2pa: false` の画像（ロゴ画像など）は最小限のフィールドのみが返る。エージェントはこの結果を見て、たとえば「この記事に使われている画像はAI生成か」「どのツールで作られたか」を機械的に判断できる。

### 有効化確認コマンド（Bash）

```bash
curl -s https://your-site.example | grep webmcp
```

**解説**: エッジ注入が正しく行われているかを確認するための最小限のコマンド。レスポンスHTML中に `/.webmcp/bridge.js` を参照するスクリプトタグが含まれているかを `grep` で確認する。

## ユースケース

### コンテンツの来歴（真正性）確認

`scan_images_c2pa` / `inspect_image_c2pa` を使い、エージェントがページ内の画像がAI生成かどうか、誰がどのツールで作成・編集したかを機械的に確認できる。ファクトチェック、ニュース記事の検証、画像の出所調査といった用途に直結するユースケースとして記事内で紹介されている。

### サイト自身のMCPサーバーをそのままエージェントに公開

すでにMCPサーバーを持っているサイト（例: `search_products` のようなツールを公開しているECサイト）は、`data-mcp-url` を指定するだけで、そのツール群をブラウザ経由でもエージェントに公開できる。エージェントはページを操作する代わりに、直接ツールを呼び出して検索・注文などのタスクを実行できるようになる。

### 既存のMCPクライアント／エージェントとの相互運用

登録されるツールはMCP標準の `Tool` / `CallToolResult` 型に準拠しているため、すでにMCP対応済みのエージェントフレームワークやクライアントは、追加の実装なしにこのページ上のツールを呼び出せる。記事ではBrowserRunがすでにこの仕組みに対応していることが紹介されている。

### 再デプロイ不要のツール拡張

ツールパック単位で機能を有効化・無効化できるため、サイト運営者はコード変更や再デプロイを行うことなく、ダッシュボード操作だけでエージェント向けの機能を追加・変更できる。

## 所感・ポイント

- 最大の特徴は「オリジン側のコード変更ゼロ」で導入できる点にある。エッジでの1行注入という最小の変更で、既存サイトをエージェント対応させられるという設計は、Cloudflareのエッジプラットフォームならではの強みを活かした実装だと感じる。
- ツールの実行が「訪問者自身のブラウザ内」で行われ、Site MCP Serverパックの通信も「訪問者自身のセッション（`credentials: "same-origin"`）」を使う点は重要である。エージェントがサイトを操作する際も、認証・権限の境界は人間のユーザーがブラウザで操作する場合と変わらないという設計になっている。
- 「静的パック（事前定義ツール）」と「動的パック（起動時にサーバー側から発見するツール）」という2つのパターンを併用する設計は、サイト側の実装コストと表現力のバランスを取るための現実的な選択に見える。すでにMCPサーバーを持つサイトは動的パックでそのまま公開でき、持たないサイトはCloudflare提供の静的パック（Content Credentialsなど）だけでも最低限のエージェント対応ができる。
- 現時点でC2PAの署名検証が行われていない（`signatureVerified: false` 固定）点は、あくまでdeveloper previewの実装として妥当な制約だが、実運用でコンテンツの真正性を厳密に判断する用途には向かない点に注意したい。
- Chrome 146という具体的なバージョンで実験的に搭載されるとされており、WebMCPというブラウザ標準自体がまだ発展途上であることが伺える。ブラウザ非対応時はブリッジスクリプトが何もせず終了する設計になっているため、既存サイトへの導入リスクは低く抑えられている。
