## TL;DR

- ウェブのトラフィックは、人間だけが対価を支払う構図から変わった。Cloudflare の平均リクエスト数は 2024 年末の 6,300 万/秒から 1.15 億/秒（ピークは 1.5 億超）に増え、過去 1 年で AI エージェント由来の日次リクエストは **1,700% 以上**増加。今年初めて、インターネットのトラフィックの**半分以上が人間ではなくなった**。
- エージェントは人間でも従来のボットでもない「第二の読者」。広告には反応しないが、背後には用事を抱えた人がいる。サービスの側が受け入れ方を整えれば収益源（additive）に、そうでなければコストの押し付け（extractive）になる。
- 記事は 4 つの柱で整理する。**誰が来ているかを見る**（AI Crawl Control、Business Insights、BotBase、Web Bot Auth）、**条件を決める**（Search / Agent / Training の個別制御、Disallow AI Training）、**対価を得る**（Pay Per Use、Monetization Gateway。いずれもベータ）、**リクエストのコストを下げる**（Markdown for Agents、WebMCP、OpenAI との共同研究）。
- これらは x402 や Web Bot Auth などの**オープン標準**の上で動き、ドメイン所有者は自分の ID プロバイダー・決済事業者・エージェントのパートナーを選べる。「Cloudflare は選択肢の 1 つであり、スタック全体ではない」という立場を取る。

## 背景・課題

これまでウェブは「検索エンジンにクロールさせる → 訪問者が来る → 広告や購読で収益化する」という取り決めの上で回ってきた。「見つけてもらうこと」と「対価を得ること」が同じ意味だった。

回答エンジン（answer engine）はページを読んで要約を返すため、サイトには帯域のコストがかかるのに、広告や決済が発生する人間の訪問は生まれない。記事が示す数字は次のとおり。

- 小売、ソフトウェア、IT サービス、金融サービスなど、特にクロールの多い業種では、1 年足らずで人間のトラフィックが最大 **40%** 減った。
- AI 学習目的のクローラーの割合は、2025 年春の **22%**（クローラーの自己申告する目的ベース）から 2026 年 6 月には **52%** になった。
- 自動化されたリクエストは帯域・計算・オリジンの処理能力を消費し続けるが、参照元も広告表示も購読もないものが増えている。つまり「1 リクエストあたりの収益が下がり、コストが上がる」。

Cloudflare は昨年、新規ドメインで AI 学習クローラーをブロックすることを勧めた。しかし「すべてに No」という一律の対応は、今つくられつつあるインターネット経済には粗すぎる、というのが記事の認識である。

### 「トラフィックの一部は顧客である」

エージェントがテーブルを予約する、保険の見積もりを比べる、研究者のためにデータセットを購入する。これらは人間ではない顧客である。自動化トラフィックで最も伸びているのはクローラーではなくエージェントで、チャットボットに人が何かを尋ねた結果として、人の代わりにページを取得する。そのトラフィックには週単位のリズムがあり、夏休みには減る（人間の行動と同じ）。エージェントを追い返すと、エージェントを送り出した人を追い返すことになりうる。

学習用クローラーが「モデルを作るためにページを集める」のに対し、エージェントは「誰かがそのコンテンツについて尋ねるたびに戻ってくる」。そのため、トラフィックは公開した量ではなく、人々が尋ねる質問の量に比例して増える。

記事は、見えない相手・区別できない相手・条件を設定できない相手・課金できない相手とは商売ができないと述べ、この 4 つを順に解消していく構成になっている。

## 発表内容 / アーキテクチャ

記事は新機能の仕様を詳述する型ではなく、Birthday Week 期間の関連発表をつなぐ総論で、各製品の詳細は個別記事（本文中のリンク先）に委ねている。本リポジトリの時点では、個別記事は未収録のため、ここでは本記事の記述の範囲でまとめる。

### 1. 誰が来ているかを見る

- 「AI ボット」という括りはもはや意味を持たず、重要なのは**何をするか**。Cloudflare の **AI Crawl Control**、**Business Insights**、**BotBase** で、誰がクロールし、何を持っていき、何が返ってくるか、どの URL が狙われているかが分かる。
- ボットの名前は信頼できて初めて意味を持つ。**Web Bot Auth** では、OpenAI、Google、AWS などの運営者がエージェントのリクエストに暗号署名を付け、サイト側は IP アドレスや user-agent 文字列から推測せずに本物か偽装かを判別できる。Cloudflare は毎週 **5,000 億件超**の検証済みボットのリクエストを観測している。

### 2. 条件を決める

- 7 月に、単一の「AI ボットをブロック」のスイッチを、**Search / Agent / Training** の 3 つの個別制御に置き換えた（Free を含む全プランで利用可能）。データによると、検索クローラーをブロックするサイトは **1% 未満**、学習をブロックするサイトは **17%**。サイト運営者は隠れたいのではなく、「見つけてもらいたいが、搾取はされたくない」。
- 検索と学習を兼ねる**混在用途クローラー**では、片方を断るともう片方も断ることになる。9 月 15 日に出した **Disallow AI Training** は、検索のインデックスは維持しつつ、クローラー固有の仕組みで運営者に「学習には使うな」と伝える。Apple、Google、Microsoft が順守を約束している。**Cloudflare Radar** もクローラーの挙動を公開で追跡している。
- 新規ドメインには、「どのソフトウェアが来たか」ではなく「そのサイトがどう収益を得ているか」に基づく推奨設定が表示される。広告で運営するサイトなら、広告は人が見て初めて支払われるため、学習を禁止し、広告を載せたページではエージェントをブロックしやすい。設定はいつでも変更できる。

### 3. 対価を得る

- 8 月に Cloudflare は目指すインターネットを「読める・見つかる・呼べる・支払える（readable, discoverable, callable, payable）」と説明した（[the-agentic-internet](./2026-08-06-the-agentic-internet.md)）。最後の payable が、オープンウェブが自力で資金を得られるかを決める。必要なのは二択の yes/no ではなく「yes, if you pay」という返事。
- ライセンス市場: 2023 年以降、出版社と AI 企業の契約は **50 件超**。ほぼすべてが個別の二者間契約で、大手同士のもの。コンテンツに価値があることは示すが、ウェブの大半にも、大半の買い手にも届かない。
- すべての資産を同じ売り方にはできない。高価値のコンテンツやデータセットには、買い手が識別され、使い方を報告する「信頼されたネットワーク」が要る。API や MCP ツールは、リクエストごとが利用そのものなので別の仕組みになる。そこで 2 つの製品を用意する。

| 製品 | 状態 | 狙い | 仕組み |
|---|---|---|---|
| **Pay Per Use** | ベータ | 個別ライセンスが届かないサイトに届く橋渡し | クロールには課金せず、コンテンツが**実際に使われたとき**に支払う。買い手はすべて検証済みクローラー。買い手が「使用」の定義と価格を決め、利用を報告し、Cloudflare が報告を検証して買い手に請求し、出版社に支払う。出版社はオファーを見て、オプトイン/アウトを選べる |
| **Monetization Gateway** | クローズドベータ（対象は米国の該当する Cloudflare 顧客） | アカウントや API キーでは取れない「一度きりの 1 回の参照」のような価値を取引可能にする | Rules 言語で Cloudflare を通るものに価格を付ける。ルールに一致したら、オープンな **x402** プロトコルで **HTTP 402 Payment Required** を返し、エージェントが売り手に直接支払う。課金はリクエスト単位・クエリ単位・トークン単位で、固定または上限付き |

- **Pay Per Use の報告の意義**: 出版社は何がいつ使われ、いくら稼いだか、買い手が報告する場合はどんな質問がそのコンテンツを引き出したかまで見える。ライセンス契約ではめったに得られない情報で、何を書き、更新し、エージェントに提供するかの判断に使えるフィードバックループになる。
- **使用の定義は 1 つではない**: 検索エンジンの引用、リサーチエージェントの引用、ショッピングエージェントによる購入完了では生まれる価値が違う。買い手は同じレールの上で複数のビジネスモデルに参加でき、出版社側に新たな統合は要らない。例として、購読者数千人の海洋エンジニア向け業界誌でも、個別契約は望めなくても、参加する AI 企業が使うたびに対価を受け取れる。
- **Monetization Gateway の例と反応**: 広告で成り立つスポーツ統計サイトが、エージェントが「アシスト数でリーグ首位は誰か」と尋ねるたびに 1 セントの何分の一かを課金できる。発表時に数千の売り手がウェイトリストに参加し、最も多かった要望は「人間ではなくエージェントに課金したい」。Cloudflare 自身が最初の顧客で、AI Gateway は Monetization Gateway を使ってエージェントが推論に支払えるようにしている。
- 買い手にとっては、どちらもブロックページより良い（安定したアクセスと、個別のライセンスや API キーなしに多数のサイトへ届く経路）。支払いごとに、何を買い、支払ったかの**レシート**が残る。
- 2 つは、ID、計量（metering）、価格設定、決済、分析という共通のプリミティブの上に作られている。publisher は 1 つのダッシュボードから「学習は禁止、検索は許可、AI の回答で稼ぎ、エージェントには記事ごとに課金」と組み合わせられる。価格設定と発見はまだ解決されていないため、両方ともベータで、実際の顧客と取引に形づくられる、としている。

### 4. リクエストを安くする

- 支払いは収益の減少への答えで、コストの上昇は別の問題で、多くは無駄。クローラーの多くは、数段落のテキストを得るために、人間向けに作られたページを繰り返しダウンロードする。前回から変更のないサイトを再クロールすることも多い。サイト側の帯域とクローラー側の計算が、回答が書かれる前に消費される。ダッシュボードでは、運営者ごとの帯域消費が見えるようになった。
- 7 月に発表した **OpenAI との共同研究**（Cloudflare のネットワークから得た知見で、AI 検索エンジンが関連コンテンツをより効率よく見つけてインデックスできるかを探る前例のない試み）の初期結果を、数週間以内に共有する予定。
- 顧客向けには、**Markdown for Agents**（スタイリングなどの人間向け要素なしでページを読める）と **WebMCP**（どのボタンを押すかエージェントに推測させず、サイトがアクションを直接公開する）を紹介している。

### なぜ Cloudflare 上で作るのか

- ウェブの **20% 超**が Cloudflare のネットワークの背後にあり、主要 AI 企業の**約 80%** も同様。市場の両側を見ており、可視性・ID・制御・決済のレールを作り、価値の決定は市場に任せる。
- 一握りの企業がエージェントの発見・本人証明・支払いを握る世界と、それらが誰でも実装できるオープン標準になっている世界があり得る。Cloudflare は後者を選ぶ。そのため x402 や Web Bot Auth のようなオープン標準を使い、ドメイン所有者が ID プロバイダー、決済事業者、エージェントのパートナーを選べるようにしている。
- 締めくくりの一文: 数十年間ウェブは訪れる人々が支払ってきたが、今は人々に代わって訪れるソフトウェアも、その分を支払える。

## コード例

本記事には**コードブロックやコマンドなどのコード例は含まれない**。ブログ総論にあたる記事で、各機能の実装や API の詳細は個別記事に任されている。代わりに、上記の「発表内容 / アーキテクチャ」で 4 つの柱と、Pay Per Use・Monetization Gateway の課金フローを整理している。記事中にあるコード的な記述は、HTTP ステータスコード `402 Payment Required` と、x402、Web Bot Auth、Disallow AI Training などのプロトコル名・機能名にとどまる。

## ユースケース

- **広告で運営するニュースサイト**: 学習を禁止（Disallow AI Training）、検索クローラーは許可、広告を載せたページではエージェントをブロックする。広告は人が見て初めて支払われるため。
- **小規模な業界誌**: 個別の AI ライセンス契約は望めなくても、Pay Per Use に参加し、参加する AI 企業が使うたびに対価を得る。どんな質問で使われたかも把握できる。
- **統計・データ API を提供するサイト**: Monetization Gateway で、エージェントの 1 回の参照ごとに少額を課金する（x402 と HTTP 402）。
- **AI 企業・エージェントの運営者**: Web Bot Auth でリクエストに署名し、検証済みクローラーとして Pay Per Use の買い手になる。ブロックされずに多数のサイトへ、正規のルートでアクセスできる。
- **自社サイトを最適化したい運営者**: Markdown for Agents で人間向けの装飾なしにページを提供し、WebMCP でサイトの操作を直接公開して、エージェントの無駄な取得を減らす。

## 所感・ポイント

- 具体的な機能の新発表というより、Birthday Week の各記事（Web Bot Auth、Disallow AI Training、Pay Per Use、Monetization Gateway、Markdown for Agents など）を 1 本の物語にまとめた「導入・総論」の記事。細部を知りたい場合は記事中のリンク先を辿る構成。
- 数字が多い記事である。63M→115M requests/s、エージェント 1,700% 増、トラフィックの半分超が人間でない、人間のトラフィック最大 40% 減、学習クローラー 22%→52%、検索ブロック 1% 未満に対し学習ブロック 17%、検証済みボット 5,000 億/週。いずれも Cloudflare 自身のネットワークでの観測であり、集計の前提（定義や期間）は原文で確認するとよい。
- 「ブロックか許可か」の二択ではなく、「yes, if you pay」という第三の選択肢を置くのが主張の核。ブロック一辺倒だった昨年の方針からの転換が読み取れる。
- Pay Per Use と Monetization Gateway はどちらもベータ（後者は米国の一部顧客向けクローズドベータ）で、記事自身が「価格設定と発見はまだ解決されていない」と書いている。現時点では方向性の提示として読むのが適切。
- 最後にオープン標準（x402、Web Bot Auth）であることと、Cloudflare は「選択肢の 1 つ」と強調している。一方で、記事は Cloudflare がウェブの 20% 超と主要 AI 企業の約 80% を見ている立場でもあるため、中立性の見方は読者が判断する余地がある。
- **サンプル対象外**: 中心となる Pay Per Use はベータで、Monetization Gateway はクローズドベータ（米国の該当する顧客のみ）のため、第三者が再現できる一般利用可能な機能ではない。記事自体も総論でコード例を持たず、100 行前後の最小実装で要点を体験できるものではないので、`examples/` は作成していません。
