## TL;DR

- Model Context Protocol（MCP）の新仕様 `2026-07-28` がリリースされ、MCPは**ステートフルなプロトコルからステートレスなプロトコルへ**と大きく作り変えられた。
- `initialize`/`initialized` のハンドシェイクと `Mcp-Session-Id` ヘッダーが不要になり、各リクエストが単独で完結するようになった。これにより `McpAgent`（Durable Object）を使わずとも、通常のCloudflare Workers上でMCPサーバーを動かせるようになった。
- サーバーからクライアントへの追加情報要求（elicitation）は、オープンストリームに依存しない **Multi Round-Trip Requests（MRTR）** という新しいリクエスト/レスポンス方式に置き換えられた。
- HTTPリクエストに `Mcp-Method` / `Mcp-Name` ヘッダーが追加され、ゲートウェイやWAFがJSON本文をパースせずにルーティング・レート制限・メトリクス収集を行えるようになった。
- 認可（authorization）まわりも強化され、CIMD（Client ID Metadata Documents）の採用、RFC 9207（issuer識別）・RFC 8707（リソース audience）への準拠が進んだ。DCR（Dynamic Client Registration）は非推奨となり、2027年夏以降に廃止予定。
- 機能の「Active / Deprecated / Removed」という正式なライフサイクルポリシーが導入され、非推奨化から最低12か月の移行期間が保証されるようになった。

## 背景・課題

Cloudflareは2025年3月にAgents SDK向けの `McpAgent` プリミティブをリリースして以来、MCPサーバー構築を積極的に支援してきた。`McpAgent` はDurable Objectsを土台にしており、コンピュート・永続的なトランザクションストレージ（組み込みSQLite）・リアルタイムのコネクション維持を1つにまとめた「ステートフルなサーバー」として、MCPが本来必要とする双方向・継続的なやり取りを実現するには最適な選択肢だった。

しかし、この設計には裏返しの課題があった。従来のMCPプロトコルはセッションの確立を前提としており、サーバーは `Mcp-Session-Id` によってクライアントとの対話状態を保持し続ける必要があった。これはオートスケールするインフラにとって重荷になる。アクティブなセッションを維持したままスケールイン・デプロイの切り替えを行う必要があり、インスタンスが失われればクライアントは再接続を強いられたり、セッションが壊れたりする。サーバーレス基盤の上でMCPサーバーを動かすこと自体は可能だが、実際にはほとんどのやり取りが必要としないはずの「セッション調整」のコストを常に払うことになっていた。

つまり記事が指摘する本質的な課題は、「MCPというプロトコルの複雑さの多くが、実際には必要とされていないステートフルネスに由来している」という点にある。この課題に対する回答として登場したのが、2026-07-28仕様によるステートレス化である。

## 発表内容 / アーキテクチャ

### MCPはステートレスになった

新しい2026-07-28仕様では、必須だったハンドシェイク、`Mcp-Session-Id` ヘッダー、そしてプロトコルセッションという概念そのものがコアのリクエストパスから取り除かれた。各リクエストは、それが必要とするプロトコルバージョン・クライアントの識別情報・クライアントの能力（capabilities）をリクエスト自身の中に含むようになる。サーバーを事前に調べたいクライアントは任意で `server/discover` を呼べるが、これはオプションであり必須ではない。

この変更により、MCPサーバーは「リクエストを受け取り、ツール・プロンプト・リソースを呼び出し、結果を返す」という単純なモデルで動作できるようになった。保存すべきプロトコルセッションが存在しないため、MCPの複雑さの大部分が取り除かれつつ、期待される機能性はそのまま維持される。

結果として、`McpAgent`（＝Durable Objects）は必須ではなくなった。アプリケーション自体が状態を必要とする場合にはDurable Objectsは引き続き適切な選択肢だが、MCPプロトコルを話すこと自体にはもはやDurable Objectは不要になった。サーバーは通常のCloudflare Workersのような「リクエストスコープのインフラ」の上でより速くスケールできる。

Cloudflareの Agents SDK はリリース当初から新仕様をサポートしており、仕様が最終化される前からリリース候補版を本番トラフィックで使ってきた顧客・パートナーの存在が、`McpAgent` から新しい `createMcpHandler`（後述）への移行パスが実運用に耐えることの裏付けになっている。

### elicitationはオープンストリームを必要としなくなった

MCPサーバーがリクエストを完了する前に追加情報を必要とする場面は多い。デプロイツールが本番リリース前に承認を求める、デザインツールがユーザーに色の選択を求める、課金ツールが返金前に確認を求める——MCPはこうしたやり取りを「elicitation」と呼ぶ。

従来、`elicitation/create` のようなサーバー起点のリクエストはオープンストリームに依存していた。そのためサーバーのデプロイでは、ストリームの複雑さ・コスト・リクエストタイムアウトのバランスを取る必要があった。

新しい仕様ではこれを **Multi Round-Trip Requests（MRTR）** という仕組みで作り直している。サーバーは必要な情報を記述した `input_required` という結果を返す。クライアントはその回答を集め、その入力を添えて元の操作をリトライする。すると元の操作を完了できる——しかも両者ともトランスポートセッションを保持し続ける必要がない。

これは従来のelicitationのやり方から見ると破壊的変更（breaking change）だが、運用面ではるかに実装しやすくなっており、より多くの開発者がこの機能を活用してリッチなエージェント型アプリケーションを構築できるようになると記事は述べている。

### HTTPインフラがMCPを理解できるようになった

MCPリクエストはHTTP上で送られるJSON-RPCメッセージだが、これまでリクエストに関する情報（どのメソッドを呼んでいるか等）はJSON本文の中にしか存在しなかった。ゲートウェイがそのリクエストが `tools/list` なのか、ツール呼び出しなのか、リソース読み取りなのかを知るには、本文をパースするしかなかった。

新仕様ではStreamable HTTPリクエストに `Mcp-Method` と `Mcp-Name` ヘッダーを含めることが求められる。例えばツール呼び出しは次のようになる。

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" }
  }
}
```

これにより、ゲートウェイ・レートリミッター・WAFは任意のJSONをパースせずにヘッダーだけで判断できるようになる。オペレーターはメソッドごとに異なるルールを適用したり、ツール単位のメトリクスを既存のHTTPプリミティブを使って記録したりできる。

さらに `tools/list`・`prompts/list`・`resources/list`・`resources/read` の結果には `ttlMs` と `cacheScope` というキャッシュ用のヒントが追加された。ツールカタログは決定的な順序で返されるようになり、クライアントは再接続をまたいでもカタログを再利用でき、アップストリームのプロンプトキャッシュを安定させられる。

![Mcp-MethodとMcp-Nameヘッダーの例を示す図](https://blog.cloudflare.com/_emdash/api/media/file/01KZA53A660J99FJBX7DAWZ4MZ.png)

### 認可（Authorization）のさらなる進化

新仕様はMCPの認可周りも厳格化した。サーバーとクライアントの間に既存の関係がある場合は事前登録済みクライアントを優先し、動的な登録には Client ID Metadata Documents（**CIMD**）を使い、Dynamic Client Registration（**DCR**）はフォールバックという優先順位になった。DCRは新規実装では非推奨となり、2027年夏以降に廃止が予定されている。

また、RFC 9207（issuer識別）を採用した。認可サーバーは `authorization_response_iss_parameter_supported: true` を提示し、成功時の認可レスポンスに `iss` を含める。クライアントはこれを、認可フロー開始前に発見したissuerと比較する。これにより、あるissuerからの認可レスポンスが別のissuerからのものと混同されることを防ぐ。

このほか、実運用で見えていた細かなギャップを埋める変更もある。MCPクライアントは、正規化されたサーバーURIをRFC 8707の `resource` として認可・トークンリクエストに含めるようになった。トークンはそのaudience向けにのみ発行され、そのaudienceでのみ受理されなければならない。

Workers OAuth Providerは、Workers上のMCPサーバー向けにこれらの要件をすべて実装している。ハンドラー関数を次のようにラップするだけでよい。

```typescript
import { OAuthProvider } from "@cloudflare/workers-oauth-provider";

export default new OAuthProvider({
  apiRoute: "/mcp",
  apiHandler: mcpHandler,
  defaultHandler: authorizationHandler,
  authorizeEndpoint: "/authorize",
  tokenEndpoint: "/oauth/token",
  clientIdMetadataDocumentEnabled: true,
  resourceMetadata: {
    resource: "https://mcp.example.com/mcp",
    authorization_servers: ["https://mcp.example.com"],
    scopes_supported: ["mcp:read"],
  },
});
```

### 成熟した標準のためのライフサイクル

技術的な変更はこのリリースの一部にすぎない。MCP 2026-07-28では、機能の正式なライフサイクルポリシーも導入された。機能は Active・Deprecated・Removed のいずれかに分類され、非推奨化された機能は削除されるまで最低12か月間は利用可能であり続けなければならない。

このリリースで非推奨となったのは、Roots・Sampling・Logging・Dynamic Client Registration、そして従来のHTTP+SSEトランスポートである。ただし、既存の実装には明確な移行期間が用意されている。このポリシーにより、チームは突然の廃止に反応するのではなく、アップグレードを計画するための最低限の時間を得られる。またコアプロトコル自体が安定する余地も生まれる。

新しいアイデアは、コアプロトコルにすぐ組み込まれる代わりに「Extensions（拡張）」というフレームワークを通じてより速く動けるようになった。MCP AppsとEnterprise-Managed Authorizationはすでにこの拡張として提供されており、Tasksも信頼性の高い長時間実行タスクを実現するパスとしてこちらに移された。実装者は必要に応じてこれらの機能を採用できる。

### 新しいSDK群

2025年11月、CloudflareはAgents SDKに `createMcpHandler` を導入した。これはMCP TypeScript SDK側の実験的なステートレスモードの上に構築されたもので、ツール・プロンプト・リソースのみを使うMCPサーバーを、より低い複雑さ・コスト・デプロイの手間でCloudflare Workersにデプロイできるようにするものだった。

今回のリリースで、この `createMcpHandler` が公式のMCP TypeScript SDKに正式採用（graduate）されることになった。

2026年初めには、MCP TypeScript SDKをNode.jsからWeb Standardsへと再プラットフォーム化する作業にもCloudflareが協力しており、Bun・Deno・Cloudflare WorkersといったJavaScriptランタイム間の相互運用性向上に寄与した。バンドリング・ランタイムシム・パッケージ分割といった貢献により、デプロイサイズが小さくなり、エコシステム全体が恩恵を受けている。

顧客は古い仕様との後方互換性を保ちながら新仕様へ移行できる。`/mcp` エンドポイントは新プロトコルと、2025年のStreamable HTTPクライアントからのステートレスなリクエストの両方を受け付けるため、ほとんどのクライアントは設定変更なしに再接続できる。

一例として、Cloudflareは2月にCloudflare API全体を対象とした Code Mode MCP Server を、この非公式なステートレスモードと `WebStandardsStreamableHTTPServerTransport` を使ってリリースしている。それ以来、毎秒数千リクエストの規模までスケールし、累計で数十億回のツール呼び出しを処理してきた。

## コード例

記事には3種類のコード例が含まれている。いずれもMCP v2仕様の技術的な変更点を裏付けるものである。

### 例1: `Mcp-Method` / `Mcp-Name` ヘッダーを含むリクエスト

「HTTPインフラがMCPを理解できるようになった」節で示されている、ツール呼び出しリクエストの生の姿。

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" }
  }
}
```

**解説**: JSON-RPC本文自体は従来どおり `method: "tools/call"` と `params.name: "search"` を持つが、それと同じ情報が `Mcp-Method: tools/call` / `Mcp-Name: search` としてHTTPヘッダーにも重複して載っている点がポイントである。ゲートウェイやWAFはJSON本文を一切パースせず、このヘッダーだけを見てルーティング・レート制限・監査ログの記録判断ができるようになる。`MCP-Protocol-Version` ヘッダーで仕様バージョン（`2026-07-28`）も明示されている。

### 例2: Workers OAuth Providerによる認可のラップ

「認可（Authorization）のさらなる進化」節で示されている、Workers上でMCPサーバーを認可付きで公開する設定例。

```typescript
import { OAuthProvider } from "@cloudflare/workers-oauth-provider";

export default new OAuthProvider({
  apiRoute: "/mcp",
  apiHandler: mcpHandler,
  defaultHandler: authorizationHandler,
  authorizeEndpoint: "/authorize",
  tokenEndpoint: "/oauth/token",
  clientIdMetadataDocumentEnabled: true,
  resourceMetadata: {
    resource: "https://mcp.example.com/mcp",
    authorization_servers: ["https://mcp.example.com"],
    scopes_supported: ["mcp:read"],
  },
});
```

**解説**: `OAuthProvider` は `apiRoute`（実際のMCPエンドポイント）と `apiHandler`（MCPリクエストを処理するハンドラー）、`defaultHandler`（認可フロー用のハンドラー）を受け取り、`/authorize` と `/oauth/token` の2エンドポイントを自動的に用意する。`clientIdMetadataDocumentEnabled: true` によってCIMDベースの動的クライアント登録を有効化しており、これが記事で説明されている「事前登録済みクライアント → CIMD → DCR（非推奨）」という優先順位のうち、CIMDに対応する設定にあたる。`resourceMetadata.resource` にMCPサーバー自身の正規URIを指定することで、RFC 8707に基づくaudience制限付きトークン発行の土台になる。

### 例3: `createMcpHandler` を使った最小構成のMCPサーバー

「新しいSDK群」節で示されている、公式MCP TypeScript SDKとCloudflare Agents SDKを組み合わせた最小サーバーの例。

```typescript
import { McpServer } from "@modelcontextprotocol/server";
import { createMcpHandler } from "agents/mcp/server";
import { z } from "zod";

function createServer() {
  const server = new McpServer({
    name: "hello-server",
    version: "1.0.0",
  });

  server.registerTool(
    "hello",
    {
      description: "Return a greeting",
      inputSchema: { name: z.string().optional() },
    },
    async ({ name }) => ({
      content: [
        {
          type: "text",
          text: `Hello, ${name ?? "World"}!`,
        },
      ],
    }),
  );

  return server;
}

export default {
  fetch(request, env, ctx) {
    return createMcpHandler(createServer)(request, env, ctx);
  },
}
```

**解説**: `McpServer`（公式SDK）に `registerTool()` で `hello` という単純なツールを1つ登録し、`zod` でスキーマ（`name` は任意の文字列）を定義している。ポイントは最後の `export default` 部分で、Cloudflare Agents SDKの `createMcpHandler(createServer)` が、通常のWorkersの `fetch` ハンドラーとしてそのまま呼び出せる関数を返している点である。以前の `McpAgent` はDurable Objectのクラスとして実装する必要があったが、この例ではDurable Objectも `Agent` クラスの継承も一切登場せず、素のWorkersハンドラーとしてMCPサーバーが完結している。これが「ステートレス化」がコードレベルにもたらした最も分かりやすい変化である。

## ユースケース

### 既存のMcpAgent（Durable Object）サーバーの移行

`McpAgent` で構築された既存のMCPサーバーを、状態管理が実際に必要な部分だけDurable Objectsに残しつつ、それ以外を `createMcpHandler` によるステートレスなWorkersハンドラーに置き換えるという移行シナリオ。記事では、ステートレスなルートを既存のセッションフルなルートと並行稼働させ、機能を少しずつ移してアクティブなセッションをドレインさせたのち、非推奨期間の終わりにレガシーパスを削除する、という段階的な移行手順が説明されている。MCPクライアント側は `agents` パッケージをアップグレードするだけでよい。

### ゲートウェイ層でのルーティング・レート制限・可観測性

`Mcp-Method` / `Mcp-Name` ヘッダーにより、既存のHTTPゲートウェイ・WAF・レートリミッターの仕組みをそのままMCPトラフィックに適用できるようになる。JSON本文をパースする専用ロジックを実装しなくても、メソッドやツール名ごとに異なるルールを適用したり、ツール単位のメトリクスを収集したりできる。

### 承認・確認フローを伴うエージェント型アプリケーション

MRTR（Multi Round-Trip Requests）による elicitation は、デプロイ承認・デザインツールでの色選択・返金確認のような「途中でユーザーの追加入力を必要とする」ワークフローに向いている。オープンストリームを維持する必要がなくなったことで、こうした承認フローをステートレスなサーバーレス環境上でも実装しやすくなった。

### エンタープライズ規模でのセキュアなMCPサーバー公開

Workers OAuth Providerを用いることで、CIMD・RFC 9207・RFC 8707に準拠した認可を、コード側でOAuthプロトコルの詳細を意識せずに実現できる。記事で紹介されているSentryやLinearのように、既存の製品データをMCP経由で様々なAIクライアントに安全に公開するユースケースに直結する。

### 大規模トラフィックを捌くAPIラッパー型MCPサーバー

Cloudflare自身のCode Mode MCP Server（Cloudflare API全体をラップしたMCPサーバー）が、この非公式ステートレスモードを先行採用し、毎秒数千リクエスト・累計数十億回のツール呼び出しという規模で実運用されてきた実績が紹介されている。ステートレスなMCPサーバーが、通常のHTTPワークロードと同じスケーラビリティを持つことを示す事例である。

## 所感・ポイント

- 今回の変更の本質は「MCPからDurable Object的な状態を追い出した」ことに尽きる。プロトコルレベルのセッションという、多くのユースケースでは不要だった複雑さを取り除いたことで、MCPサーバーは実質的に「ツール呼び出しを受けてレスポンスを返すだけの、ふつうのHTTP API」に近づいた。これはCloudflare Workersのようなリクエストスコープの実行環境と非常に相性が良い設計変更だと感じる。
- MRTR（elicitationのリトライ方式への置き換え）は一見地味だが、「オープンストリームを張り続ける」という運用上の負債を丸ごと解消する設計転換であり、影響範囲は大きい。承認待ちのようなヒューマン・イン・ザ・ループを伴うエージェントアプリケーションを、サーバーレス環境で気軽に作れるようになる点は実務上のインパクトが大きそうだ。
- `Mcp-Method` / `Mcp-Name` ヘッダーの追加は、MCPを「特別なプロトコル」から「既存のHTTPインフラの語彙で扱えるプロトコル」へ寄せていく方向性を象徴している。JSON-RPCの中身を意識しなくてもゲートウェイ側で制御できるというのは、既存のAPI基盤にMCPを統合する上での障壁を大きく下げるはずだ。
- Deprecated機能に最低12か月の移行猶予を設けるライフサイクルポリシーは、仕様がまだ若いにもかかわらず「エコシステムを壊さずに進化させる」という成熟した運用姿勢を感じさせる。Extensions（MCP Apps・Enterprise-Managed Authorization・Tasksなど）という別レイヤーを用意し、コア仕様を小さく保つ設計判断も、長期的な安定性を意識したものだろう。
- SentryやLinearが「移行しても壊れなかった」と証言している点は、実運用に耐える設計変更だったことの裏付けとして説得力がある。特にDurable Objectベースの `McpAgent` に依存していた既存実装ほど、記事内の移行ガイドを事前に確認しておく価値が大きいだろう。

> **Workers サンプル**: [examples/mcp-v2/](../../examples/mcp-v2/) — `createMcpHandler` を使い、Durable Object不要のステートレスなMCPサーバーを素のWorkersで動かす最小実装。
