# 読み取り、発見、呼び出し、決済が可能なオープンなエージェンティックインターネットの構築

## TL;DR

- Cloudflareの観測データによると、良性ボットの大量トラフィックの多くが「前回のクロール以降変わっていないページ」を再取得しており、計算資源が成果を生まないまま消費されている。
- この背景には、Webの新しい訪問者層である「エージェント」の台頭がある。エージェントは新種のソフトウェアではなく、新種のサイト訪問者だと記事は位置づける。
- Cloudflareは、Webサイトを「読み取り可能（Readable）」「発見可能（Discoverable）」「呼び出し可能（Callable）」「決済可能（Payable）」の4つの性質を備えたものにすることで、オープンな「エージェンティックインターネット」を構築しようとしている。
- この4つのプリミティブはいずれもオープン標準（x402、MCP、Web Bot Auth、PACT など）に基づいており、Cloudflareは自社スタックへの囲い込みではなく、ドメイン所有者が自由にアイデンティティ・決済・エージェントパートナーを選べる中立的基盤を志向する。
- 具体的な実装として、Markdown for Agents、Kitesurf、AI Search、Agent Engine Optimization（AEO）、WebMCP、Code Mode、Wallets、Monetization Gateway などの一群のツール・仕様が紹介されている。

## 背景・課題

Webサイトへのアクセスは長らく「人間がブラウザで見る」ことを前提に設計されてきたが、記事はまずCloudflareの観測データを引いて、現実はすでにそうなっていないと指摘する。良性ボットによる膨大な数のリクエストのうち相当量が、コンテンツが変わっていないページの再取得に費やされており、ドメイン所有者側の配信コストとエージェント側の取得コストの双方が、誰の役にも立たないまま無駄になっている。

この無駄が生じる根本原因は、Webの提供側・計測側の設計が「エージェントという新しい種類の訪問者」を想定していない点にある。エージェントはCSSをレンダリングせず、ヒーロー画像を眺めることもなく、広告をクリックすることもない。しかし記事が強調するのは、そのエージェントの向こうには必ず「お金を払う人間」がいるという点である。つまり各リクエストには必ず費用負担者と目的が存在しており、これを単純に「迷惑なスクレイパー」として一律ブロックすれば、それは同時に自社の顧客をブロックすることにもなりかねない。逆に無防備に受け入れれば、成果のないアクセスにコストを払い続けることになる。

記事はここから、インターネットの将来を二つのシナリオで対比させる。ひとつは、発見・認証・決済の仕組みを少数の巨大プラットフォームが独占し、それ以外のプレイヤーがその仲介を通じてしかエージェントとやり取りできなくなる「悲観的シナリオ」。もうひとつは、標準化された実装可能なプリミティブと公開されたコード、中立的な基盤インフラによって、誰もが対等に参加できる「楽観的シナリオ」である。Cloudflareは後者の実現に貢献する立場を取ると宣言しており、本記事はその具体的な方法論の解説にあたる。

## 発表内容 / アーキテクチャ

### エージェントという新しい訪問者

記事は、従来ブラウザがUser-Agentヘッダーで自身の身元を伝えていた構図が変化し、いまや「ユーザーエージェント」という言葉が文字通り「ユーザーの代理人」として機能し始めていると説明する。人に代わってWeb上の情報を取得・操作するプログラムが日常的に動いており、その中でも最も成熟した例がコーディングエージェントである。コーディングエージェントはコードを読み書きし、必要なドキュメントを取得し、ページを解読しながら作業を進める。この延長線上に、あらゆる業務ドメインのエージェントが登場しつつある、というのが記事の見立てである。

### エージェンティックインターネットの経済的な分かれ目

現行のWebのビジネスモデル（広告収益、ページビュー計測など）は、エージェントによる大量アクセスをほとんど想定していない。記事は、エージェントが「読み取り、発見、呼び出し、支払う」ための仕組みが今後どう整備されるかが、インターネットのオープン性が保たれるか閉鎖的な少数支配に向かうかを左右すると論じる。ここでCloudflareが担う役割として明言されているのは、あくまで選択肢の一つとしての基盤提供であり、スタック全体を独占する立場ではないという点である。ドメイン所有者は自身のアイデンティティプロバイダー、決済処理業者、エージェントパートナーを自由に選べる。Cloudflare自身も、特権的な経路や早期アクセスAPIを持たず、顧客と同じ基盤を使う「カスタマー・ゼロ」として自らの仕組みを検証する立場を取ると述べられている。

### 4つのプリミティブ: Readable / Discoverable / Callable / Payable

記事の中核は、Webサイトが備えるべき4つの性質を軸にした整理である。

#### 1. 読み取り可能（Readable）

エージェントがコンテンツをネイティブに読み取れることが前提になる。エージェントは人間向けの装飾的なHTMLタグを見ないため、それらは計算資源の無駄であるだけでなく、エージェントのコンテキストウィンドウを不要な情報で汚染してしまう。この課題に対応するのが **Markdown for Agents** で、サーバーサイドでコンテンツをエージェント向けのMarkdown形式に変換し、帯域幅とトークン消費を削減する。またクライアントサイドの対応として、Workers上で動作する軽量ブラウザ **Kitesurf** が紹介されている。Kitesurfはリクエストごとに起動・破棄できる設計で、人間向けの表示機能を持たず、エージェントに必要な機能のみを提供する点が特徴。

#### 2. 発見可能（Discoverable）

発見可能性はエージェンティックインターネットにおける経済活動の起点と位置づけられる。エージェントがそもそもそのリソースの存在を知らなければ、読み取りも呼び出しも決済も成立しない。記事は、検索インターフェースはもはやキーワード入力ボックスだけでは不十分で、エージェント向けのインターフェースが必須になると述べる。この文脈で **AI Search** は、公開サイトをエージェントが検索可能な状態にする仕組みとして紹介され、**Agent Engine Optimization（AEO）** はコンテンツクリエイターやAPI所有者が、自分たちのコンテンツがエージェントからどの程度「見えている」かを測定するための考え方として提示される。顧客が利用するエージェントから測定可能なレベルで見えていないサイトは、実質的にオフラインと同じだと記事は強調する。

#### 3. 呼び出し可能（Callable）

エージェントがサイトの「機能」を実行できることを指す。レストランの予約、サブスクリプションの更新、レポート作成といった操作が例に挙がる。従来、人間向けに作られたWebサイトの構造は見た目もマークアップもサイトごとに大きく異なり、エージェントがそれらを操作しようとするとHTML解析とボタン位置の推測、クリック操作の合成に頼らざるを得ず、DOM構造が変わるたびに壊れやすい。これに対して **WebMCP** は、サイト側がブラウザを通じて自らの操作をエージェントに明示的なツールとして公開する仕組みであり、HTML解析やフォームフィールドの推測が不要になる。さらにページ内で完結するため、ユーザーの既存セッションや状態をそのまま再利用できる利点もある。

もう一段進んだ概念として **Code Mode** が紹介される。エージェントは自然文よりもコードとして思考し、コードとしてツールを呼び出す方が高速かつ正確であるという考え方に基づき、HTMLスクレイピングではなく明示的なエンドポイント呼び出しによって操作を行う。これにより、サイト所有者から見てもどのコンテンツが実際に使われているかが明確になる。

#### 4. 決済可能（Payable）

記事はこれをエージェンティックインターネットの未来像の核と位置づける。経済的な取引が成立する以上、支払い手段が必須になる。従来の広告モデルは、エージェントが広告を見ない・クリックしないという前提のもとでは機能しない。シート課金モデルもプログラムから呼び出されるユーザーには馴染まず、ページビューに依存する出版社は、広告を非表示にされた場合に活動資金を確保しづらくなる。

これに対し記事は、新しい収益モデルの可能性として、レシピサイトが広告収益化に失敗しても1回の取得あたり1セント未満の対価で採算が取れる可能性や、地方紙が長期のライセンス契約やログインを求めずに、記事閲覧の都度その場で一時的なライセンスを許諾できる可能性を挙げる。エージェント側は人間があらかじめ設定した財布（ウォレット）と予算の範囲内で活動する。またすべての有料取引で領収書が発行され、出版社側は「どのエージェントがどのページを取得したか」を証明でき、エージェント側は「対価を支払った」ことを証明できるという透明性が担保される。

具体的なツールとして、エージェントがコンテンツやAPI利用料を簡単に支払える **Wallets**、ドメイン所有者が数クリックでエージェント向けの課金設定を行える **Monetization Gateway** が挙げられている。

### Cloudflareの立場

記事の終盤では、Cloudflareが元来、数十億の人間とその訪問先サイトの間に立ち、保護・通信高速化・可用性維持を担ってきた立場であることが再確認される。トラフィックの主体が人間からエージェントへとシフトしても、この「仲介者として信頼される中立的なレイヤーであり続ける」という役割自体は変わらないという整理である。出版社、加盟店、エージェントビルダー、エンドユーザーのいずれとも競合しない中立的な高性能レイヤーであり続けることが、Cloudflareの立ち位置として述べられている。

## コード例

記事内には、「呼び出し可能（Callable）」セクションでWebMCPの説明箇所に、JavaScriptによるツール登録のコード例が1つ掲載されている。

```javascript
document.modelContext.registerTool({
  name: "add-todo",
  description: "Add a new item to the user's active todo list",
  inputSchema: {
    type: "object",
    properties: {
      text: { type: "string", description: "The todo item text" }
    },
    required: ["text"]
  },
  async execute({ text }) {
    await addTodoItemToCollection(text);
    return { content: [{ type: "text", text: `Added: "${text}"` }] };
  }
});
```

**解説**: `document.modelContext.registerTool()` は、ブラウザ上で動作するページ自身が「自分にはこういう操作ができる」とエージェントに向けて宣言するためのAPIである。`name` と `description` はエージェントがどのツールをいつ使うべきかを判断する手がかりとなり、`inputSchema` にはJSON Schema形式で入力パラメータの型・説明・必須項目（ここでは `text` という文字列のTodo項目テキスト）を定義する。`execute` に渡された非同期関数が実際の処理本体で、この例では既存のアプリケーション関数 `addTodoItemToCollection(text)` を呼び出したうえで、実行結果を `content` 配列としてエージェントに返している。

従来型の自動操作であれば、エージェントはHTMLを解析して「Todoを追加するボタンらしきもの」を推測し、クリックイベントを合成し、DOM構造が変わらないことを祈りながら操作する必要があった。このコード例が示すのは、そうした不安定な推測を挟まず、サイト側が最初から「明示的なツール契約」としてボタンの背後にある処理を公開するアプローチである。これにより、HTML解析やフォームフィールドの推測が不要になり、かつユーザーがすでにブラウザ上に持っているログインセッションや状態をそのまま利用しながら処理を実行できる。

## ユースケース

### 変わらないページの無駄な再取得を減らす

記事冒頭で提示される課題そのものがユースケースの出発点になっている。良性ボットが変更されていないページを繰り返し取得している現状に対し、Markdown for AgentsやAI Search、AEOのような「読み取り可能」「発見可能」にする仕組みを整えることで、エージェントが本当に必要な情報だけを効率よく取得できるようにし、ドメイン所有者・エージェント双方の無駄な計算コストを削減する。

### Todoリスト・予約・サブスクリプション管理などの操作代行

コード例で示されたWebMCPは、Todoリストへの項目追加を題材にしているが、記事本文ではレストランの予約、サブスクリプションの更新、レポート作成といった操作もCallableの対象として挙げられている。人間が9往復のやり取りをして初めて完了していた作業を、エージェントが1回のやり取りで完結させられるかどうかが、ユーザーから見た体験改善の指標になるとされる。

### 少額課金によるコンテンツマネタイズ

広告モデルが機能しないエージェント向けアクセスに対して、WalletsとMonetization Gatewayを組み合わせ、1回の取得あたり1セント未満といった小口決済でコンテンツを収益化するユースケースが挙げられている。レシピサイトのような広告収益化が難しいコンテンツや、地方紙のように長期契約やログインを前提にできない媒体において特に有効とされる。

### エージェント向けの一時ライセンス許諾

地方紙の例のように、記事閲覧のたびにその場で一時的なライセンスをエージェントに許諾し、都度課金する仕組みも挙げられている。長期の契約交渉やアカウント発行を前提とせず、取引の都度、透明性のある領収書を発行することで、出版社・エージェント双方が取引の正当性を証明できる状態を作る。

## 所感・ポイント

- 本記事は個別の新製品発表というより、「エージェントというWebの新しい訪問者層に対して、Webサイト全体がどう振る舞うべきか」という原則論を、Readable / Discoverable / Callable / Payable という4分類に整理した宣言的な記事だと捉えるとわかりやすい。個々の技術要素（Markdown for Agents、Kitesurf、WebMCP、Code Mode、Wallets、Monetization Gatewayなど）は、この4つの性質に対応する形で位置づけられている。
- 「ボット＝悪、人間＝善」という単純な二分法をやめ、エージェントのアクセスにも望ましい振る舞いと望ましくない振る舞いの両方があるという捉え方は、これまでのボット対策一辺倒の議論からの明確な転換だと感じる。適切なプロトコルと経済的インセンティブ（少額決済・領収書による透明性）を用意することで、望ましくない振る舞い（無断の大規模スクレイピング、ブロック回避、robots.txt無視）を減らし、望ましい振る舞いへ誘導しようという発想は、技術だけでなく経済設計としても興味深い。
- x402・MCP・Web Bot Auth・PACTといった既存のオープン標準の名前を挙げつつ、「Cloudflareはあくまで選択肢の一つであり、スタック全体を独占しない」と明言している点は、一見するとCloudflareにとって不利にも見える主張だが、裏を返せば「エージェンティックインターネットが特定ベンダーに閉じたものになると、供給側の多様性が失われ、結局はインターネット全体の価値が下がる」というオープン性への長期的なコミットメントの表明とも読める。
- WebMCPやCode Modeのように「ページのHTML構造に依存せず、明示的な契約でエージェントに操作を公開する」という設計思想は、フロントエンド開発者にとって今後のAPI設計・アクセシビリティ設計の延長線上で理解しやすいテーマである。既存のREST APIやGraphQL APIの設計知見が、そのままエージェント向けツール設計に転用できる場面も多いと考えられる。

> **Workers サンプル**: 対象外（Readable/Discoverable/Callable/Payableという原則を整理した概念記事であり、個別のWorkersサンプルは各要素技術の記事（[webmcp](./2026-08-06-webmcp.md)、[kitesurf](./2026-08-06-kitesurf.md)など）側に用意している）。
